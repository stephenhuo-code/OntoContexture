### Session 2026-10-04

## User Scenarios & Testing *(mandatory)*

本特性的产出是“后续 23 个特性在哪里写、怎么写、怎么连起来”。使用者是架构负责人、各特性的开发者
与评审人。

### User Story 1 - 覆盖全部 Phase 1 特性的平台技术架构 (Priority: P1)

架构负责人需要一份覆盖 Phase 1 全部 24 个特性的平台技术架构：平台划分为哪些服务与前端应用、每个
服务的职责边界与数据归属、服务之间如何通信（同步接口、异步事件、MCP）、外部组件（元数据与本体
平台、身份服务、轨迹存储、本体实例库、管线编排器、Agent 运行时、执行沙箱）放在哪里、跨切面能力
（身份与委托令牌、租户隔离、查询审计、可观测、统一取数）由谁提供、各服务如何接入。架构以
架构文档与 ADR 的形式评审通过后，作为后续特性 plan 阶段的依据。

**Why this priority**: 没有整体架构，各特性会各自决定服务怎么拆、数据放哪、怎么调用，重复造轮子、
边界冲突，后期难以合并。宪法 II 要求按能力域拆分服务、独占数据、契约先行，必须先有全局划分。

**Independent Test**: 从计划中任选一个特性，仅凭架构文档就能回答：它落在哪个服务或应用、依赖哪些
服务与存储、通过什么方式调用、使用哪些公共能力；评审人对 24 个特性逐一核对均能回答。

**Acceptance Scenarios**:

1. **Given** Phase 1 的 24 个特性，**When** 查阅架构文档，**Then** 每个特性都被分配到明确的服务、
   前端模块或外部组件配置，没有无归属的特性，也没有两个服务争抢同一职责。
2. **Given** 任一服务，**When** 查阅架构文档，**Then** 能看到它的职责、独占的数据存储、对外接口
   类型、依赖的服务与外部组件。
3. **Given** 计划第 4 节中尚未成文的决策（多租户隔离方式、对象类型在元数据平台上的实现方式、仓库
   结构、数字员工平台），**When** 本特性完成，**Then** 每项都有已接受的 ADR。
4. **Given** 架构文档，**When** 按宪法逐条检查，**Then** 没有违反 II（服务边界与数据独占）、IV
   （身份、授权、审计）、V（可观测）、VI（开源组件以服务方式集成）的设计。

### User Story 2 - 统一的代码架构与公共能力 (Priority: P1)

各特性的开发者需要统一的代码架构：仓库的目录划分、单个服务内部的分层方式、接口与事件契约放在哪里
及版本规则、配置与错误处理的约定，以及所有服务共用的公共库——鉴权与租户上下文、委托令牌处理、
可观测关联属性、本体读取、经 AI 网关的 MCP 取数客户端、统一错误格式。服务模板按这些约定生成，开发者不需要
在每个服务里重新实现跨切面能力。

**Why this priority**: 跨切面能力（尤其身份、租户、可观测）如果每个服务各写一份，宪法 IV、V 的
要求无法保证一致；统一代码架构也决定后续特性能否并行开发。

**Independent Test**: 用服务模板新建一个服务，不写任何跨切面代码，确认它已具备：验证令牌并取得
人、Agent、租户；按统一属性输出日志与追踪；经公共的 MCP 取数客户端发起查询；以统一格式返回
错误。

**Acceptance Scenarios**:

1. **Given** 代码架构文档，**When** 开发者要新增一个服务或一个接口，**Then** 能确定代码放在哪个
   目录、分几层、契约放在哪里、如何版本化。
2. **Given** 由模板生成的新服务，**When** 收到一个不带有效令牌或令牌租户与资源租户不一致的请求，
   **Then** 由公共库统一拒绝，服务代码无需额外处理。
3. **Given** 由模板生成的新服务，**When** 处理一次请求，**Then** 日志与追踪自动带上租户、人、Agent、
   运行或会话等关联属性（ADR-0001）。
4. **Given** 一个服务需要访问实例数据，**When** 开发者使用公共的 MCP 取数客户端，**Then** 请求经 AI 网关
   到达数据库 MCP 服务，服务本身不持有数据库账号（ADR-0013）。

### User Story 3 - 端到端骨架贯通各层 (Priority: P1)

架构负责人需要一条最小的纵向切片真实跑通，证明架构可行：用户登录织境 Web → BFF 从元数据与本体平台
读取一个已审批的对象定义 → BFF 经 AI 网关以 MCP 查询本体实例库 → 结果返回界面。全程带委托令牌与租户，
AI 网关记录取数审计，并在追踪中看到完整调用链。Phase 1 不做数据层授权（宪法 IV 例外，ADR-0012、0013）。

**Why this priority**: 架构只有跑起来才能暴露问题（如令牌传递、租户上下文、追踪串联、服务间契约）。
越早在最小切片上暴露，后续特性越少返工。

**Independent Test**: 在本地环境部署骨架，以一个测试租户的用户登录并触发示例查询，确认界面显示
结果、审计中有记录、一条追踪覆盖从界面到存储的每一跳。

**Acceptance Scenarios**:

1. **Given** 已部署的骨架与一个测试租户用户，**When** 用户在织境 Web 发起示例查询，**Then** 界面
   返回来自本体实例库的数据，并展示对应对象类型的定义。
2. **Given** 同一次请求，**When** 查看追踪，**Then** 一条追踪串起界面、BFF、元数据与本体平台、AI 网关、数据库 MCP 服务与
   存储访问，每一跳带相同的关联属性。
3. **Given** 另一租户的用户，**When** 发起同样的查询，**Then** 看不到前一租户的数据。
4. **Given** 同一次请求，**When** 查看查询审计，**Then** 能看到人、Agent（若有）、租户、查询摘要与返回行数。

### Edge Cases

- 某特性的职责同时落在两个服务的边界上：架构文档需给出归属规则（按数据归属判定），不允许双写。
- 外部组件（如元数据平台）不可用时：示例服务返回明确错误并记录追踪，不吞掉错误。
- 令牌过期、租户不匹配：由公共库统一处理，返回一致的错误格式。
- 追踪在跨越异步边界（事件、管线任务）时断链：架构需规定异步场景的关联属性传递方式。
- 公共库升级导致服务不兼容：公共库有版本，升级需在骨架上回归通过。
- 架构中尚未确定的决策影响多个特性：在对应 ADR 中写明影响范围与临时约定。

## Requirements *(mandatory)*

### Functional Requirements

**平台技术架构**

- **FR-001**: 本特性 MUST 产出平台技术架构文档，覆盖 Phase 1 全部 24 个特性，给出服务与前端应用
  划分、每个服务的职责、独占数据存储、对外接口类型、依赖关系。服务按能力域拆分，一个服务可承载
  多个特性，MUST NOT 按特性一对一拆分；每个服务的拆分理由写入架构文档（宪法 II）。
- **FR-002**: 架构 MUST 规定服务间通信方式及适用场景（同步接口、异步事件、MCP），以及跨服务的
  身份、租户与关联属性如何传递（含异步场景）。
- **FR-003**: 架构 MUST 规定跨切面能力的归属与接入方式：身份与委托令牌（002，Keycloak 标准令牌交换）、
  取数审计与统一取数（006，AI 网关 + MCP Toolbox，ADR-0013）、轨迹与追踪（009，Langfuse）、管线编排（ADR-0006）；Phase 1
  不做数据层授权（宪法 IV 例外）。
- **FR-004**: 架构 MUST 标明外部组件（元数据与本体平台、身份服务、轨迹存储、本体实例库、管线编排器、
  Agent 运行时、执行沙箱）的部署位置与集成方式，并遵守宪法原则 VI。
- **FR-005**: 计划第 4 节尚未成文的四项决策（多租户隔离方式、对象类型在元数据平台上的实现方式、
  仓库结构、数字员工平台）MUST 各形成已接受的 ADR。
- **FR-006**: 架构文档与新增 ADR MUST 经架构评审，无阻塞问题后方可视为完成。

**代码架构**

- **FR-007**: 本特性 MUST 产出代码架构文档，规定仓库目录划分、服务内部分层、接口与事件契约的位置
  与版本规则、配置与错误处理约定。
- **FR-008**: 系统 MUST 提供公共库，覆盖：令牌验证与人 / Agent / 租户上下文、委托令牌处理、可观测
  关联属性、本体读取（经 OM 只读已审批内容）、经 AI 网关的 MCP 取数客户端、统一错误格式。
- **FR-009**: 公共库 MUST 对缺少有效令牌、租户不匹配的请求统一拒绝，业务代码不需重复实现。
- **FR-010**: 服务模板 MUST 按代码架构生成服务骨架并默认接入全部公共库，生成后测试即可通过。
- **FR-011**: 公共库与服务模板 MUST 有版本，升级需在端到端骨架上回归通过。

**端到端骨架**

- **FR-012**: 系统 MUST 提供可运行的端到端骨架：织境 Web 登录 → BFF → AI 网关 → 数据库 MCP 服务 → 本体实例库，BFF 经公共库
  从元数据与本体平台读取已审批的对象定义，结果返回界面。
- **FR-013**: 骨架中的每一跳 MUST 传递委托令牌与租户并输出可串联的追踪；AI 网关 MUST 记录取数审计（人、Agent、租户、工具与查询摘要）。
- **FR-014**: 骨架 MUST 验证跨租户隔离：一个租户的用户无法看到另一租户的数据。
- **FR-015**: 取数路径 MUST 只读（数据库只读账号），并设置超时与返回行数上限。

### Key Entities

- **服务目录**：平台全部服务与前端应用的清单，每项含职责、归属特性、独占存储、接口类型、依赖。
- **架构决策（ADR）**：对影响多个特性的技术选择的记录，含背景、决策、影响与被否决方案。
- **公共库**：所有服务共享的跨切面能力实现，有版本。
- **服务模板**：按代码架构生成新服务的起点，默认接入公共库。
- **端到端骨架**：贯穿各层的最小可运行切片，用于验证架构与回归公共库。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Phase 1 的 24 个特性 100% 在架构文档中有明确归属；评审人随机抽查任一特性，5 分钟内
  能确定其服务、依赖与调用方式。
- **SC-002**: 计划第 4 节尚未成文的 4 项决策 100% 形成已接受的 ADR。
- **SC-003**: 新开发者阅读代码架构文档后，能在 30 分钟内用模板创建一个服务并跑通其测试。
- **SC-004**: 由模板生成的服务无需编写任何跨切面代码，即通过身份、租户隔离、审计与追踪的验收测试。
- **SC-005**: 端到端骨架的一次用户请求在一条追踪中覆盖全部跳数（100%），跨租户访问测试 100% 失败。

## Assumptions

- 已接受的 ADR 是本特性架构设计的输入：轨迹存 Langfuse（0001）；Agent 框架为 Omnigent（0002）；自建统一
  前端（0003）；本体定义在 OpenMetadata、实例在 Doris（0004）；统一取数（0005）；独立部署的 Airflow（0006）；
  多租户（0007）；本体六要素（0008）；OM 的构建与部署（0011）；Phase 1 精简自建服务（0012）；数据访问与 AI 网关（0013）。
- 自建服务使用 Python（FastAPI），前端技术栈按 ADR-0003；身份服务为 Keycloak。
- 骨架中的身份、取数路径（AI 网关 + MCP Toolbox）、前端外壳均为最小实现，分别由 002、006、003 完善；本特性确定它们的接口与接入方式。
- 骨架使用 004 之前的少量手工测试数据；完整的模拟工厂数据由 004 提供。
- 骨架至少能在本地开发环境运行；CI 门禁、多环境部署与离线打包按宪法要求在 plan / tasks 的准备阶段
  搭建，不在本 spec 中定义验收；离线安装包只支持 x86_64，不考虑信创。
- 上游补丁机制按宪法原则 VI 在首次需要时（008、011）落实。
