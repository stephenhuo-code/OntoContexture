# Feature Specification: 003 模拟工厂数据集与模拟源系统

**Feature Branch**: `003-mock-factory-data`

**Created**: 2026-10-23

**Status**: Draft

**Input**: User description: "开始写003，按照讨论的思路来，数据要支持3个实际的案例场景"

## 一句话

003 做完后，本地环境里有一家**假的、但像真的**汽车零部件工厂：模拟的 MES、QMS 和数仓三套“客户系统”，里面是一条命令生成的
一年生产与质量数据，并且埋好了 **3 个带标准答案的案例**。后续特性（元数据采集、指标、上下文、追溯、飞书关联）都拿它开发、测试和
演示，不必等真实客户。

## 范围说明

- 本特性交付 Phase 1 计划中 003 的**第一批：工厂数据库**，外加 3 个案例。飞书测试租户（第 ③ 批）在 010 交付，20 个追溯案例
  （第 ④ 批）在 019 交付，帆软报表 SQL 样例在 024 交付；它们都复用本特性的工厂、人员与编号体系。
- 只交付“数据 + 生成程序 + 模拟系统”，不做任何界面，不接入织境的其他组件（采集在 011 做）。
- 数据全部是合成数据，不含任何真实客户或个人信息。

## Clarifications

### Session 2026-10-23

- Q: “3 个实际案例场景”选哪 3 个？ → A: C1 设备故障追溯、C2 来料不良追溯（P1），C3 一次合格率口径分歧（P2），覆盖 Phase 1 的两个验收场景。

## 3 个案例场景

案例取自 POC 场景路线图中 Phase 1 覆盖的两个场景：P1 质量问题追溯与 8D 协同、P2 探索式报表。每个案例都有一份
**标准答案**，后续特性的验收直接对照它。

| 编号 | 场景 | 故事 | 标准答案（节选） |
| --- | --- | --- | --- |
| C1 | P1 追溯：设备故障 | 2 号线一台数控车床主轴轴承磨损，某两天内加工的 3 个批次外径尺寸超差；客户退货后 QMS 开出客诉 NCR | 入口 NCR 号 → 涉及的 3 个批次 → 工单与工序 → 同一台设备 → 该时段的检验记录与超差值 → 当班班组与操作工；同一设备在此前出现过的预警记录 |
| C2 | P1 追溯：来料不良 | 某供应商一个毛坯批次硬度偏低，装配后多个工单在终检出现裂纹，开出内部 NCR | 入口 NCR 号 → 不良成品批次 → 使用的物料批次 → 同一供应商批次 → 同批次物料流向的其他工单（含尚未发现问题的）→ 来料检验记录 |
| C3 | P2 问数：指标口径分歧 | 业务问“上个月 2 号线一次合格率”，按“返工后合格算合格”与“只算首次合格”两种口径结果不同，帆软现有报表用的是前者 | 两种口径的定义、计算所用的表与字段，以及各自在指定月份、产线上的准确数值 |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 一条命令得到一家模拟工厂（Priority: P1）

开发人员在本地环境执行一条命令，模拟的 MES、QMS 与数仓作为三套独立的“客户系统”被部署起来，并灌入默认规模（约一年、百万行级）
的工厂数据。之后任何人都能用普通数据库客户端连上去，看到表、字段说明和数据。

**Why this priority**: 后续所有用数据的特性（采集、指标、上下文、追溯）都以它为前提。

**Independent Test**: 在已部署 001 的本地环境执行生成命令，用数据库客户端连接三套系统，核对表清单、字段说明和行数。

**Acceptance Scenarios**:

1. **Given** 001 的本地环境已运行，**When** 执行生成命令（默认规模），**Then** 三套模拟系统可连接，表与字段都有中文说明，
   行数达到默认规模，且命令输出各系统的连接方式与数据摘要。
2. **Given** 已生成过一次数据，**When** 用相同参数再执行一次，**Then** 数据被重建且与上次逐行一致。
3. **Given** 已生成过一次数据，**When** 换一个规模参数执行，**Then** 数据量按参数变化，3 个案例仍完整存在。

---

### User Story 2 - 3 个案例可以按标准答案复现（Priority: P1）

产品负责人或测试人员拿到案例说明与标准答案，直接在模拟系统里按 NCR 号、批次号查询，查到的记录与标准答案一致。后续特性
（追溯、问数、上下文）的验收也以这些答案为准。

**Why this priority**: 没有标准答案就无法判断后续 Agent 的追溯和问数是否正确，这是“支持实际案例”的核心。

**Independent Test**: 对每个案例，按案例说明里给出的查询步骤在模拟系统中查询，逐项比对标准答案。

**Acceptance Scenarios**:

1. **Given** 数据已生成，**When** 以 C1 的 NCR 号为入口逐步查询，**Then** 查到的批次、设备、检验超差值、班组与标准答案完全一致。
2. **Given** 数据已生成，**When** 以 C2 的 NCR 号为入口追到物料批次，再查该物料批次的全部流向，**Then** 受影响工单清单与标准
   答案完全一致，包括尚未出现问题的工单。
3. **Given** 数据已生成，**When** 按 C3 两种口径分别计算指定月份、产线的一次合格率，**Then** 两个数值与标准答案一致，且二者不同。
4. **Given** 案例数据埋在大量正常数据中，**When** 查看案例时段内的其他批次与设备，**Then** 它们没有同类异常，不会干扰判断。

---

### User Story 3 - 集成测试按需加载小规模数据（Priority: P2）

开发人员写集成测试时，能在测试启动的临时数据库里加载一份小规模、同结构的工厂数据（含 3 个案例），测试结束即丢弃。

**Why this priority**: 宪法要求集成测试使用真实依赖；小规模数据让测试又快又真实。

**Independent Test**: 在一个只启动临时数据库的测试中加载小规模数据，断言表结构与案例记录存在，并计时。

**Acceptance Scenarios**:

1. **Given** 一个空的临时数据库，**When** 测试加载小规模数据，**Then** 30 秒内完成，表结构与默认规模一致，3 个案例完整。

---

### User Story 4 - 后续特性有一份可依赖的数据说明（Priority: P2）

后续特性的开发者（元数据采集、指标、飞书关联、追溯）查阅一份数据说明，就知道工厂的组成、每张表的含义、跨系统靠哪些编号关联，
以及人员与班组名单（010 搭飞书测试租户时照此建人）。

**Why this priority**: 编号体系和人员名单一旦被后续特性引用就不宜再改，需要一开始就写清楚。

**Independent Test**: 拿数据说明对照模拟系统，抽查表、字段、关联键与人员名单是否一致。

**Acceptance Scenarios**:

1. **Given** 数据说明，**When** 随机抽取 10 个字段对照模拟系统，**Then** 名称、含义与实际一致。
2. **Given** 数据说明中的跨系统关联键（批次号、工单号、NCR 号、工号、设备编号、物料批次号），**When** 在三套系统间按这些键关联，
   **Then** 关联全部成立。

### Edge Cases

- 本地资源不足以生成指定规模：命令在开始前估算所需空间并给出明确提示，不留下半成品数据。
- 生成中途失败或被中断：再次执行即可从头重建，结果与一次成功执行相同。
- 模拟系统尚未就绪就执行生成：等待就绪或给出明确错误，而不是部分写入。
- 规模参数取到最小值：3 个案例仍完整，标准答案不变。
- 数据时间范围：所有日期相对一个固定的“基准日”生成，与执行当天无关，保证可复现。
- 案例与正常数据“撞车”：正常数据中不得随机出现与案例同类、可能被误判为案例的异常。

## Requirements *(mandatory)*

### Functional Requirements

**工厂与数据**

- **FR-001**: 模拟一家汽车零部件工厂：机加工与装配两类工艺、2 条产线、约 20 台设备，以及与之配套的物料、供应商、班组与人员。
- **FR-002**: 提供三套相互独立的模拟系统：MES（批次、工单、工序报工、设备、设备事件、操作工、物料批次与投料）、QMS（来料检验、
  过程与终检检验、缺陷码、NCR / 客诉、8D 历史）、数仓（明细层与汇总层样例表，含按产线、按日的合格率等汇总）。MES 与 QMS 使用
  不同类型的数据库，模拟客户的异构环境。
- **FR-003**: 每张表、每个字段都带中文说明，能被通用数据库客户端和元数据采集工具读取。
- **FR-004**: 数据之间关系真实：工单引用存在的批次与设备，报工时间与设备、班次一致，检验记录对应真实工序，NCR 关联真实批次与缺陷，
  数仓汇总可由明细数据重算得到。
- **FR-005**: 数据覆盖约一年，相对固定基准日生成；规模可通过参数调整，默认规模为百万行级，最小规模适合测试使用。
- **FR-006**: 相同参数（含随机种子）两次生成的数据逐行一致。

**案例**

- **FR-007**: 数据中埋入 3 个案例（C1 设备故障追溯、C2 来料不良追溯、C3 一次合格率口径分歧），在任何规模下都完整存在。
- **FR-008**: 每个案例提供一份说明与标准答案：故事背景、入口编号、逐步查询路径、每一步的期望记录或数值。标准答案与生成的数据一致，
  并有自动检查保证二者不会走样。
- **FR-009**: 正常数据中不出现可能被误判为案例的同类异常；案例时段内的其他批次、设备保持正常。

**使用方式**

- **FR-010**: 一条命令完成：部署三套模拟系统到本地环境、生成并灌入数据、输出连接方式与数据摘要；重复执行时重建数据。
- **FR-011**: 集成测试能在临时数据库中加载小规模数据，30 秒内完成。
- **FR-012**: 模拟系统由生成命令按需部署到本地环境（平台的一键部署不部署它们），随本地环境启停；它们是开发与测试设施，不进入组件清单与离线交付包（plan 阶段调整，见 research R4）。

**数据说明**

- **FR-013**: 提供数据说明：工厂组成、各系统的表与字段含义、跨系统关联键、编号规则、人员与班组名单。人员与班组名单可直接用于
  010 搭建飞书测试租户。
- **FR-014**: 所有姓名、工号、客户与供应商名称均为合成数据，不含真实个人或企业信息。

### Key Entities

- **工厂结构**：工厂、产线、工位、设备（含设备事件 / 预警）。
- **生产**：物料、物料批次（含供应商与供应商批次）、成品批次、工单、工序、报工（谁、在哪台设备、何时）、投料（哪个物料批次用于哪个工单）。
- **质量**：检验记录（来料、过程、终检；检验项、实测值、判定）、缺陷码、NCR / 客诉、8D 历史。
- **组织**：班组、人员（工号、岗位、所属班组、班次）。
- **数仓汇总**：按产线、按日或按月的产量、合格率等汇总。
- **案例**：案例说明、入口编号、查询路径、标准答案。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在已运行 001 环境的开发机上，一条命令 15 分钟内完成默认规模数据的部署与生成。
- **SC-002**: 相同参数两次生成，三套系统的数据逐行一致（一致率 100%）。
- **SC-003**: 3 个案例的标准答案 100% 能在模拟系统中按说明查询复现，且在最小与默认两种规模下都成立。
- **SC-004**: 跨表、跨系统关联键的有效率为 100%（不存在指向不存在记录的引用）。
- **SC-005**: 集成测试加载小规模数据（含 3 个案例）在 30 秒内完成。
- **SC-006**: 100% 的表与字段有中文说明；数据说明抽查 10 个字段全部与实际一致。
- **SC-007**: 产品负责人不读代码，按验收文档 1 小时内完成全部手动验收。

## Assumptions

- 运行在 001 交付的本地环境上；资源占用以开发机可承受为限（默认规模的磁盘占用在 plan 中给出）。
- MES 与 QMS 采用两种常见开源关系型数据库（计划为 MySQL 与 PostgreSQL），数仓表放在一个独立的模拟数仓库中，具体选择在 plan 中定。
- 模拟系统只在本地开发与测试中使用，不进入任何交付环境与离线安装包。
- 不模拟 ERP；C2 所需的供应商与供应商批次信息放在 MES 的物料批次中。
- 不注入脏数据（缺失、重复、编码不一致），数据质量问题在 020 需要时再追加。
- 不模拟设备时序数据；C1 的设备异常以设备事件 / 预警记录体现。
- 字段命名采用国内 MES / QMS 常见风格，不对标某一具体商用产品。
- 数据规模“百万行级”指三套系统合计，具体每张表的行数在 plan 中定。

## Out of Scope

- 飞书测试租户与飞书侧数据（010）。
- 20 个追溯案例与质量专家评审（019）。
- 帆软报表 SQL 样例（024）。
- 元数据采集与接入织境（011）。
- 任何界面。
