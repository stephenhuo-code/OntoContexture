# 织境 Phase 1 特性列表与开发计划

2026-11-01 修订 · 依据：《织境（Contexture）产品规划》、《织境 POC 场景路线图》、项目宪法 v2.0.0、[平台技术架构](architecture/platform-architecture.md)

## 1. 范围

Phase 1 = 产品路标“阶段一”= POC 场景 **P1 质量问题追溯与 8D 协同** + **P2 探索式报表**。
**Phase 1 按单租户设计与交付**：一套环境只服务一个客户，可有多个用户与 Agent；`tenant_id` 作为部署常量保留
（宪法 v1.5.0 部署约束的 Phase 1 例外，ADR-0007 修订）。
目标是在只读前提下让数字员工“答得准”：三域数据在一张图上、Agent 只用已审批口径、
每次调用可追溯。

| 场景 | 验证能力 | 验收指标（来自 POC 路线图） |
| --- | --- | --- |
| P1 追溯与 8D | 三域合一、决策轨迹、OKF 知识包 | 20 个历史 NCR 回放：上下文覆盖 ≥ 80%；8D D1–D4 草稿人工修改量 < 40%；追溯查询从小时级降到分钟级；轨迹可按 NCR / 人 / Agent 查询 |
| P2 探索式报表 | 指标审批、受治理取数、固化上线 | 首批 ≥ 30 个指标完成审批；问数准确率抽检 ≥ 90%；探索漏斗可查询；一个真实需求从探索到帆软上线不经人工 SQL |

**术语**：以产品规划第 3 节“术语表”为准。本计划常用的：本体（六要素：对象、关系、属性、逻辑、动作、接口；
Phase 1 只做对象、关系、属性，ADR-0008）、本体实例（存于 Doris 本体实例库，ADR-0004）、指标、分类与标签、租户、
决策轨迹、上下文包。

**Phase 1 不做**：任何写回业务系统的动作；OT 实时采集（设备、点位仅作元数据对象）；
NebulaGraph 属性图、OpenFGA、Trino、MetricFlow、CLI / API 类工具型数据源（数据库经 MCP 接入属于 009，ADR-0013）、数据契约强制执行与自动整改、治理自动化规则、
根因分析（ADR-0006）、数据层授权（按“人 ∩ Agent ∩ 数据级别”，含列级；宪法 IV Phase 1 例外，ADR-0012）
（均为二期）；多租户（是否需要另行评估，ADR-0007）；自建 ChatBI 前端；
自演进的提案生成（只从第一天起**存纠正样本**）。

## 4. 开工前要定的架构决策

以下决策影响多个特性，建议在 001 的 plan 阶段以 ADR 形式定下（`docs/adr/`），
并用 architecture-reviewer 评审：

1. **本体与实例的存储分层**（已定，见 [ADR-0004](adr/0004-本体与实例的存储分层.md)）：OM 存本体
   定义（对象类型、关系类型、属性、术语）、源系统元数据与血缘、字段映射；Doris（本体实例库）存
   全部对象实例，包括设备、产线、物料、人员等主数据与批次、工单、检验、NCR 等业务流水；两者用 URI
   关联，Doris 表结构由 016 根据本体生成。人员实例与 Keycloak 平台用户通过工号或飞书 ID 关联。
   仍需 spike 验证：10⁷–10⁸ 规模下追溯查询 P95、离线部署资源占用。
   可变深度的多跳遍历（P4 多级 BOM）不在 Phase 1，二期评估属性图或图数据库。
2. **租户**（已定，见 ADR-0007 及其 2026-10-08 修订）。Phase 1 单租户：一套环境只服务一个客户，可有多个用户与
   Agent；`tenant_id` 为部署常量。ADR-0007 的多租户设计（Keycloak Organization、各存储按租户隔离）暂缓，是否采用另行评估。
3. **本体在 OpenMetadata 上的实现方式**（已定，见 ADR-0008）。不改 OM 核心；Phase 1 直接使用 OM 的本体能力
   （术语库、审批、RDF），只做对象、关系、属性。
4. **自建服务技术栈**（已定）。自建服务统一 Python（FastAPI）；不改 OM 核心，Phase 1 无 Java 开发。
   **Agent 框架**（已定，见 [ADR-0002](adr/0002-Agent框架采用Omnigent.md)）：客户侧 Agent 与织境
   内部 Agent 统一采用 [Omnigent](https://github.com/omnigent-ai/omnigent)（Apache 2.0）。
   - 缺失能力由团队改造：持久化执行（rollout 存 PostgreSQL）、委托令牌、OTel 轨迹（多租户暂缓）
     （并关闭对外遥测）；需验证：500 并发运行、离线 + 私有化模型、以短期委托令牌作 AI 网关凭证。
   - 改造按“配置 → 扩展点 → 最小补丁”逐级选择，补丁以上游镜像仓库（子仓库 `third_party/omnigent/src/`，仓库 `stephenhuo-code/contexture-omnigent`，锁定 v0.18.0）方式维护并登记（宪法 VI）；完整工作台官方嵌入，轻量助手由织境维护，前后端必要扩展遵循同一规则，不复制上游 UI（ADR-0002 / 0003 2026-11-01 修订）。
   - 执行：取数与调模型一律经 AI 网关（009，ADR-0013）。Phase 1 对数据工程师开放终端与代码执行（数据管线、
     Airflow 开发），执行端运行在集群内的执行沙箱中（Omnigent 官方支持的 Kubernetes 沙箱，候选 agent-sandbox；ADR-0002 2026-10-23 修订），
     沙箱只持有当前用户的委托令牌，网络只放行登记的目标（AI 网关、Airflow 等）。
   - 轨迹与运行状态存储见 [ADR-0001](adr/0001-Agent轨迹与运行状态存储.md)：Langfuse 是轨迹的
     唯一真相来源；运行状态以 rollout（jsonl 逐行格式）存 PostgreSQL。
5. **仓库结构与代码架构**（已定，见 [ADR-0009](adr/0009-仓库结构与代码架构.md)）。monorepo：`apps/web/`、`services/bff/`
   （Phase 1 唯一自建服务，也是参考实现）、`packages/py-core/`（公共库）、`pipelines/`、`agents/<名称>/`、`skills/`、
   `contracts/`（含对外 MCP 工具契约 `contracts/mcp/`）、`ontology/`、`deploy/components/<组件>/`（每个开源组件一个
   标准目录：清单、Chart、参数、配置即代码与测试，CI 检查）、`extensions/`、`third_party/`（打了补丁的上游仓库）。
   Phase 1 不做服务模板。各开源组件的定制级别如下（宪法 VI）：

   | 组件 | 定制级别 | 本仓库维护的内容 |
   | --- | --- | --- |
   | OpenMetadata Server | 配置 + 扩展；以上游镜像仓库自行构建（ADR-0011） | `third_party/openmetadata/`：织境维护的 OM 仓库（子仓库），Phase 1 发布分支只含 OKF v0.2 补丁（ADR-0011、0012）；`extensions/`：帆软血缘、国产库等自定义连接器（005） |

   | AI 网关、MCP Toolbox | 仅配置 | `deploy/components/<组件>/config/`：网关路由、令牌校验、授权与审计；Toolbox 数据源与工具定义（009，ADR-0013） |

### 001 工程基座与交付流水线

- **是什么**：开发团队的“地基”，用户看不到，但之后每个特性都在它上面开发：平台技术架构与代码架构、所有自建代码共用的公共库、开源组件的统一管理方式（每个组件一个标准目录与清单）、提交代码后自动跑测试和查许可证的流水线（CI），以及一键部署到本地环境、打包成客户可离线安装的交付包（阿里云测试环境在 004 之后搭建），并以一条端到端骨架验证。例：开发者提交代码，流水线自动测试、扫描、部署到测试环境。
- **复用**：Helm（各组件的官方 Chart）、Terraform alicloud provider、kind；SBOM 与扫描工具（Syft / Grype / Trivy、ScanCode，均 Apache 2.0）；CI 平台（plan 中确定）。
- **自建**：monorepo 结构、公共库 `contexture-core`、`bff` 参考实现、组件目录与清单检查、宪法门禁流水线编排、伞形 Chart、发布验证环境、离线安装包构建。
- **问题**：宪法要求 TDD、契约优先、CI 门禁、客户云可移植交付，开工第一天就要有骨架。
- **范围**：见 `specs/001-engineering-foundation/`。平台技术架构与代码架构（ADR-0009）；公共库；OTel 关联属性规范
  （`tenant_id` 常量、人、Agent、run / session、业务对象、引用的本体与口径，见 ADR-0001）；组件目录与清单检查；
  CI：构建、单元 / 契约 / 集成测试、覆盖率 ≥ 80%、静态检查、SBOM、许可与漏洞扫描；伞形 Chart 部署 OM（自建镜像，
  开启 RDF，ADR-0011）、Keycloak、AI 网关、MCP Toolbox、OTel Collector、Langfuse、Doris、独立部署的 Airflow
  （KubernetesExecutor）；本地 kind（含本地 Keycloak）；发布验证环境；离线安装包；端到端骨架（单租户）；系统可观测
  后端选型（服务指标与日志，在 001 的 tasks 阶段确定；Grafana 系为 AGPL 不可用）。
- **验收**：参照 `bff` 新增一个接口并跑通测试 < 30 分钟；缺清单或版本未锁定的组件被 CI 拦截；故意引入的 AGPL 依赖被
  CI 拦截；本地 kind 一键部署成功；离线包可在断网 kind 集群安装；骨架一次请求在一条追踪中覆盖全部跳数。
- **宪法关注点**：I、II（契约优先）、III（SBOM、许可扫描）、V（OTel）、VI（组件以服务方式集成）、部署约束。

### 002 身份与 Agent 委托令牌

> **已取消（2026-10-23，负责人决定）**。结论：身份与委托令牌的基础已在 001 交付——Keycloak realm 配置即代码（默认角色、
> 测试用户、客户端与受众映射，增量导入不改 Paperclip 的配置）、标准令牌交换（受众收窄到 AI 网关，未知受众被拒绝）、
> 公共库 `contexture-core.auth`（验签，解析 `sub` 为人、`azp` 为 Agent）与 `contexture-core.mcp`（令牌交换）、AI 网关只接受
> 交换后的令牌、环境初始化（`make up`、`make seed`）。剩余项均可用 Keycloak 自带能力配置完成，不需要单独的开发特性：
> - Agent 客户端（打开标准令牌交换，以描述与属性记录负责人与用途）随使用方配置：Paperclip 在 011，Omnigent 示例 Agent 与
>   无人值守 Agent 的服务账号在 012；不做“登记文件生成客户端”的工具。
> - 尚未验证的身份要求在对应特性开发时验证并测试：人被禁用后其 Agent 不能再交换令牌、已有令牌过期后失效；`sub` 为人、
>   `azp` 为 Agent；交换后的令牌不能用于受众以外的服务；伪造请求头中的用户 ID 无法通过鉴权（011、012）。
> - 对接客户已有 IdP：Phase 1 不做，碰到客户需求再说。
>
> 以下为取消前的原始描述，保留备查。

- **是什么**：统一的登录与身份能力。人用企业账号登录；每个 Agent 在 Keycloak 中登记为一个“客户端”，代表某个人干活时，用人的令牌换一张同时写明“哪个人”（`sub`）和“哪个 Agent”（`azp`）、只能用于指定服务的临时通行证（委托令牌，ADR-0013）。Phase 1 单租户：一套环境一个客户，客户下有多个用户。还包括环境初始化脚本。例：张三登录后让 8D 助手查数据，系统知道是“8D 助手代表张三”在查。
- **复用**：Keycloak：OIDC 登录、**标准令牌交换**（正式功能）、client credentials、对接客户 IdP。
- **自建**（不建服务）：Agent 登记（`agents/<名称>/registration.yaml`）与生成 Keycloak 客户端、realm 配置即代码（含受众映射，`deploy/components/keycloak/config/`）与测试、公共库 `contexture-core.auth`（验签、解析人 / Agent）与 `contexture-core.mcp`（按会话与目标服务交换并缓存令牌）、环境初始化脚本。
- **问题**：宪法 IV 要求人与 Agent 各有身份、Agent 携带人的身份、只信任签名令牌。
- **范围**：使用现有 Keycloak（26.8.0），与 Paperclip 共用同一个 realm（ADR-0010）；默认角色：管理员、AI 工程师、业务用户；Agent 登记（负责人、用途）生成 Keycloak 客户端；人登录后由 Agent
  运行时以 Agent 客户端身份做标准令牌交换，受众收窄到 AI 网关等目标；无人值守 Agent 用服务账号；各服务共用的
  鉴权中间件；环境初始化脚本（创建 realm、Langfuse project、Doris 只读账号与 workload group、Toolbox 与网关配置、
  OM 初始化）；对接客户 IdP 的方式。
- **验收**：伪造请求头中的用户 ID 无法通过鉴权；人被禁用后其 Agent 无法再交换令牌、已有令牌在过期后失效；
  令牌中 `sub` 为人、`azp` 为 Agent；交换后的令牌不能用于受众以外的服务。
- **宪法关注点**：IV 全部身份条款；部署约束（Phase 1 单租户例外）。

```
/speckit-specify 实现织境的身份与 Agent 委托令牌：基于 Keycloak（一个 realm，Phase 1 单租户）为用户提供 SSO 登录，把每个 Agent 登记为 Keycloak 客户端（负责人、用途），人登录后由 Agent 运行时以 Agent 客户端身份做标准令牌交换，得到 sub 为人、azp 为 Agent、受众收窄的短期委托令牌；支持无人值守 Agent 的服务账号；提供所有服务共用的鉴权中间件、令牌交换客户端与环境初始化脚本，realm 配置即代码并带测试。生产环境需能对接客户已有 IdP。
```

### 007 Agent 工作台与页面助手

- **依赖**：004、006；基于 004 的兼容性 spike 结论；不等待 012 的执行沙箱。
- **复用**：锁定版本的 OmnigentApp、官方客户端 / 已发布 API 与服务端；001 的 BFF 鉴权与令牌交换库。

- **定稿前验证与估算**：1.5 周为暂估。先以隔离实验确认真实身份 / 会话权限、OM 上下文、SDK 与工作台同会话、
  重连 / 取消 / 退出及服务端执行拒绝；客户端依赖同版 omnigent 包，检查 BFF 依赖体积与构建兼容，再复估排期。
- **范围**：基础服务部署、BFF 转发 API / 流与 WebSocket、签名身份桥接、短期委托身份与会话级 OM MCP；
  新建对话、按项目组织会话的嵌入工作台；织境自建页面助手侧栏、选中资产与页面上下文；
  侧栏到工作台延续同一会话，保留消息与结果，返回后保留搜索条件和选中项；每条消息记录发送时的上下文，切换资产不改写历史。
  消息和运行状态以 Omnigent 为准，不建第二套会话正本；SSE 不回放历史，恢复须读取快照并处理竞态 / 去重。
  身份和令牌在服务端处理，不以假数据代替集成验收；不能安全支持的上游入口保持关闭。
- **身份与凭证接缝**：上游 OIDC / accounts Bearer 校验其自身会话令牌，Keycloak 用户识别优先验证 AuthProvider 扩展；

### 023 企业文档知识

- **是什么**：把 SOP、控制计划、历史 8D 等文件变成 Agent 能用的知识。**复用 OM 上下文中心**（文件、文章）存放与

- **复用**：OM 上下文中心（文件上传与存储、文章、审批工作流）；文档解析库（如 Apache Tika、Docling，许可在 plan 中确认）。

- **问题**：P1 需要把 SOP、控制计划、历史 8D 等文档变成 Agent 可用、可追溯、经过审批的知识。

### 024 实例物化

- **是什么**：把客户业务系统里的数据按本体整理后复制一份到 Doris 本体实例库。例：MES 工单表中的一行变成一个“工单”
  实例（统一 URI），并关联到同一个“批次”；QMS 中引用该批次的 NCR 也关联到这个批次。这样跨系统追溯（026）才能用统一
  标识在 Doris 中一次关联查询完成，不必每次实时去多个系统拼接。
- **复用**：Doris 导入能力（Stream Load / Routine Load、Unique Key 模型）；OM 中的本体与字段映射（016、018）；Airflow 调度。
- **自建**：实例物化管线（源系统 → 按本体映射转换 → 写入 Doris → 小时级增量）。
- **问题**：MES、QMS、ERP 的表结构与编号不统一，跨系统追溯需要统一标识的实例数据。
- **范围**：按本体映射把近 6–12 个月的批次、工单、检验、NCR 等实例物化到 Doris；小时级增量；在 plan 中评估 Doris 外部
  数据目录（catalog，不复制数据、直接查询源库）作为轻量备选，比较追溯性能与源库负载。
- **编排**：物化管线以 Airflow DAG 实现（ADR-0006）。
- **范围补充**：与质量专家完成 20 个带标准答案的追溯案例（5 类根因各 4 个，贯通 MES、QMS 与飞书），即 003 的第 ④ 批，供
  026 追溯与 028 回放验收。
- **验收**：模拟数据的映射覆盖率 ≥ 95%；增量摄取小时级；物化实例的 URI 与本体一致。

```
/speckit-specify 实现实例物化：按 OpenMetadata 中已审批的本体与字段映射，把近 6 到 12 个月的批次、工单、检验、NCR 等实例数据由 Airflow 管线物化到 Apache Doris 本体实例库，统一对象 URI，支持小时级增量，并评估 Doris 外部数据目录作为不复制数据的备选方案。

### 025 三域数据治理与管线编排

- **是什么**：数据接进来之后的“持续体检和保洁”。定期检查三个域的数据是否完整、及时、正确：
  核心表有没有缺数据、同步有没有延迟、源系统改了表结构后哪些本体映射失效、对象实例是否符合本体
  （比如批次必须属于某个工单）、飞书人员和 MES 工号对不对得上、消息和轨迹里有没有未脱敏的个人
  信息。发现问题自动告警，并生成待办进入审批中心。数据治理里的“数据质量”“工作流”页面在这里交付。
- **复用**：OM 的数据质量（DQ as Code、测试套件、剖析）、自动分类、数据契约、治理工作流；001 部署的
  独立 Airflow 负责调度。
- **自建**：映射漂移检测、本体一致性检查与三域对齐质量指标（以 OM 数据质量自定义测试实现，结果落
  在 OM）、工作域个人信息识别、治理待办接入审批中心、“数据质量”“工作流”页面。
- **问题**：三域接入后需要持续治理，否则 Agent 拿到的上下文会悄悄变旧、变错（ADR-0006）。
- **范围**：核心对象表（批次、工单、检验、NCR）的数据质量与新鲜度检查；自动分类覆盖源表与本体
  实例库并补充中文与工业场景规则；源表结构变化 → 映射漂移告警；P1 追溯链路涉及关系的本体一致性
  检查；三域对齐质量指标；工作域个人信息识别；治理 DAG 统一由 Airflow 编排，失败告警；治理发现
  的问题生成待办进入审批中心；“数据质量”“工作流”页面。核实 ADR-0006 第 4 节所列事项。
- **验收**：在模拟数据中注入缺失、延迟、结构变化、关系断裂、未脱敏个人信息，均能被发现并告警；
  检查结果可在 OM 与织境 Web 中查看；治理待办出现在审批中心。
- **宪法关注点**：IV（分级、个人信息）；V（管线可观测）；VI（以 OM 数据质量扩展实现自建检查）。

```
/speckit-specify 实现三域数据治理与管线编排：由独立部署的 Airflow 统一编排治理管线，复用 OpenMetadata 的数据质量、自动分类、数据契约与治理工作流，对批次、工单、检验、NCR 等核心对象表做数据质量与新鲜度检查，自动分类覆盖源表与本体实例库；自建源表结构变化导致的本体映射漂移告警、追溯链路的本体一致性检查与三域对齐质量指标（以 OM 数据质量自定义测试实现）、工作域个人信息识别；管线失败告警，治理发现的问题生成待办进入审批中心，并交付数据治理中的“数据质量”与“工作流”页面。

### 026 三域统一知识图谱与追溯查询

- **是什么**：P1 的核心能力：把系统数据、飞书工作数据、Agent 数据连成一张图。输入一个 NCR，一次拉出“批次 → 工单 → 工序 → 设备 → 检验记录 → 同批次历史问题 → 责任班组 → 相关飞书讨论”，原来要跨几个系统查几小时，目标是分钟级。
- **定位**：不建图谱服务（ADR-0012）。“图”由 OM 中的本体（对象、关系）与 Doris 中的实例组成；追溯以 SQL
  模板实现，定义为 MCP Toolbox 的参数化查询工具，经 009 的 AI 网关调用；本体映射经公共库 `ontology` 从 OM 读取。
- **复用**：Doris（多表关联查询，经 009 访问）、OM 的本体、关系与血缘。
- **自建**：三域对齐（按共同对象匹配，物化管线中完成）、追溯 SQL 模板与 Skill 工具、同批次历史问题检索、结果的来源标注。
- **问题**：P1 的核心——以 NCR 为入口一次拉通“批次 → 工单 → 工序 → 设备 → 检验 → 责任班组 → 飞书讨论”。
- **范围**：系统域、工作域、Agent 域以共同对象对齐；本体在 OM，实例与关系存 Doris；追溯 SQL 模板（Doris
  多表关联，定义为 Toolbox 工具）；同批次历史问题检索；查询结果附来源。
- **验收**：模拟数据上追溯查询分钟级以内（具体 P95 在 plan 中定）；20 个案例的追溯路径与
  标准答案一致。

```
/speckit-specify 实现三域统一知识图谱与追溯查询：把系统数据、飞书工作数据和 Agent 数据以人员、设备、工单、批次等共同对象对齐，本体在 OpenMetadata、实例与关系存于 Apache Doris；以 SQL 模板实现以 NCR 为入口的追溯查询（批次、工单、工序、设备、检验记录、同批次历史问题、责任班组、相关飞书讨论与审批），定义为 MCP Toolbox 的参数化查询工具、经 AI 网关调用，结果附来源，并封装为 Agent 可调用的 Skill 工具；不建图谱服务。
```

## 6. 每个特性的 Spec Kit 流程

每个特性独立一个分支（`NNN-<name>`），按以下顺序推进，一个特性合并后再开依赖它的特性：

| 步骤 | 命令 | 产出 / 检查点 |
| --- | --- | --- |
| 1 | `/speckit-specify <第 5 节的描述>` | `specs/NNN-*/spec.md`：用户故事、需求、可度量的成功标准 |

| 3 | `/speckit-checklist` | 按需生成安全 / 许可检查清单（004、009、012、017、025、006、007、008 必做） |

| 6 | `/speckit-tasks` | tasks.md：按依赖排序，测试任务排在实现任务之前 |
| 7 | `/speckit-analyze` | spec、plan、tasks 一致性检查，问题修完再实现 |
| 8 | `/speckit-implement`（或 TDD 版 `/speckit.tdd-implement`） | 红 → 绿 → 重构，测试先于实现提交 |
| 9 | `/speckit-converge` | 对照 spec 找出未完成项，补为任务并完成 |
| 10 | 编写手动验收文档 `acceptance.md` → 产品负责人手动验收 | 宪法 v1.6.0：不读代码可执行；问题修复后复验 |
| 11 | PR → 评审 → 合并（非 squash） | CI 全绿；评审核对测试先行、契约、许可、权限审计 |
