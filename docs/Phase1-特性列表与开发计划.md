# 织境 Phase 1 特性列表与开发计划

2026-10-03 · 依据：《织境（Contexture）产品规划》、《织境 POC 场景路线图》、项目宪法 v1.0.0

## 1. 范围

Phase 1 = 产品路标“阶段一”= POC 场景 **P1 质量问题追溯与 8D 协同** + **P2 探索式报表**。
目标是在只读前提下让数字员工“答得准”：三域数据在一张图上、Agent 只用已审批口径、
每次调用可追溯。

| 场景 | 验证能力 | 验收指标（来自 POC 路线图） |
| --- | --- | --- |
| P1 追溯与 8D | 三域合一、决策轨迹、OKF 知识包 | 20 个历史 NCR 回放：上下文覆盖 ≥ 80%；8D D1–D4 草稿人工修改量 < 40%；追溯查询从小时级降到分钟级；轨迹可按 NCR / 人 / Agent 查询 |
| P2 探索式报表 | 指标审批、受治理取数、固化上线 | 首批 ≥ 30 个指标完成审批；问数准确率抽检 ≥ 90%；探索漏斗可查询；一个真实需求从探索到帆软上线不经人工 SQL |

**术语**（与产品规划第 4 节“工业本体四层”一致）

| 术语 | 含义 | 例子 |
| --- | --- | --- |
| 工业本体 | 模型整体：对象类型、关系类型、属性、术语（L0 标准层 + L1 领域包） | ISA-95 层级、质量领域包 |
| 对象类型 / 关系类型 | 本体中定义的类型与类型之间的关系 | 对象类型“设备”“批次”“NCR”；关系“批次 → 工单” |
| 对象实例（简称“对象”） | 按对象类型存入的具体数据（L2 客户实例层） | 设备 CNC-07、批次 B2409-17、NCR-2026-0815 |
| OM 实体 | OpenMetadata 自身的技术概念（表、指标等资产的数据模型）；对象类型以 OM 实体类型实现 | OM Metric 实体 |
| 本体实例库 | 存放全部对象实例与关系实例的织境自有存储（Doris）；本体定义存于 OM；不替代客户数仓（ADR-0004） | 设备、批次、检验记录的数据行 |

**Phase 1 不做**：任何写回业务系统的动作；OT 实时采集（设备、点位仅作元数据对象）；
NebulaGraph 属性图、OpenFGA、Trino、MetricFlow、工具型数据源接入（MCP / CLI / API，ADR-0005）、数据契约强制执行与自动整改、治理自动化规则、
根因分析（ADR-0006）（均为二期）；自建 ChatBI 前端；
自演进的提案生成（只从第一天起**存纠正样本**）。

## 4. 开工前要定的架构决策

以下决策影响多个特性，建议在 001 的 plan 阶段以 ADR 形式定下（`docs/adr/`），
并用 architecture-reviewer 评审：

1. **本体与实例的存储分层**（已定，见 [ADR-0004](adr/0004-本体与实例的存储分层.md)）：OM 存本体
   定义（对象类型、关系类型、属性、术语）、源系统元数据与血缘、字段映射；Doris（本体实例库）存
   全部对象实例，包括设备、产线、物料、人员等主数据与批次、工单、检验、NCR 等业务流水；两者用 URI
   关联，Doris 表结构由 011 根据本体生成。人员实例与 Keycloak 平台用户通过工号或飞书 ID 关联。
   仍需 spike 验证：10⁷–10⁸ 规模下追溯查询 P95、每租户 database + 行策略、离线部署资源占用。
   可变深度的多跳遍历（P4 多级 BOM）不在 Phase 1，二期评估属性图或图数据库。
2. **多租户隔离方式**。OpenMetadata、OpenSearch、Fuseki 都不原生支持多租户。选项：
   按租户分索引 / 分数据集、用 OM Domains 模拟、在网关层过滤。影响 005、011、015、017。
3. **对象类型在 OpenMetadata 上的实现方式**。对象类型以 OM 实体类型（JSON Schema）实现，需改 OM 核心，宪法要求“上游 PR +
   本地扩展”双轨。需要确定扩展点、构建方式与升级策略。影响 011、013。
4. **自建服务技术栈**（已定）。自建服务统一 Python（FastAPI）；OM 核心扩展只能用 Java，
   范围限定在 011 的对象类型扩展。
   **Agent 框架**（已定，见 [ADR-0002](adr/0002-Agent框架采用Omnigent.md)）：客户侧 Agent 与织境
   内部 Agent 统一采用 [Omnigent](https://github.com/omnigent-ai/omnigent)（Apache 2.0）。
   - 缺失能力由团队改造：持久化执行（rollout 存 PostgreSQL）、委托令牌透传、多租户、OTel 轨迹
     （并关闭对外遥测）；需验证：500 并发运行、离线 + 私有化模型、OM UI 挂载 Agent 面板。
   - 改造按“配置 → 扩展点 → 补丁”逐级选择，补丁在 `third_party/omnigent/` 登记维护（宪法 VI）。
   - 执行：SQL 一律经统一取数网关（006）；Python / 数据管线在 agent-sandbox（Apache 2.0）+
     gVisor / Kata 沙箱中执行，沙箱内不放数据库账号。
   - 轨迹与运行状态存储见 [ADR-0001](adr/0001-Agent轨迹与运行状态存储.md)：Langfuse 是轨迹的
     唯一真相来源；运行状态以 rollout（jsonl 逐行格式）存 PostgreSQL。
5. **仓库结构**。建议 monorepo：`services/<服务名>`、`web/`（织境 Web 与 BFF）、`contracts/`
   （OpenAPI / AsyncAPI）、`ontology/`（本体与领域包，本体即代码）、`extensions/`（上游组件的
   扩展包）、`third_party/`（上游补丁）、`deploy/helm`、`deploy/terraform`、`testdata/`。
   按宪法 VI，各开源组件的定制级别如下（以当前设计判断，plan 阶段确认）：

   | 组件 | 定制级别 | 本仓库维护的内容 |
   | --- | --- | --- |
   | OpenMetadata Server | **补丁** + 扩展 | `third_party/openmetadata/`：新增对象类型所需的核心改动（011）；`extensions/`：帆软血缘、国产库等自定义连接器（012） |
   | Omnigent | **补丁** + 扩展 | `third_party/omnigent/`：持久化、令牌透传、多租户、OTel 所需的扩展缝隙（008）；`extensions/`：rollout 存储、沙箱提供者等实现 |
   | Keycloak | 配置，必要时扩展 | realm 配置即代码；如令牌交换需定制，用 Keycloak SPI 扩展（002） |
   | OTel Collector | 配置，必要时扩展 | 如需自定义处理器，用官方构建工具生成自有发行版 |
   | JupyterHub | 配置 + 扩展 | 经网关取数的客户端库与 spawner 配置（022） |
   | Doris、Langfuse、Jena Fuseki、OpenSearch、agent-sandbox、gVisor / Kata、lark-cli | 仅配置 | Helm values 与配置文件 |
   | openmetadata-ui | 不使用、不修改 | —（ADR-0003） |
6. **数字员工平台**。P1/P2 的消费方是谁（飞书智能伙伴、自研平台），决定 019、024 的参考
   Skill 形态和轨迹回传方式（OTLP 还是 Webhook）。
7. **前端与管理端**（已定，见 [ADR-0003](adr/0003-前端架构与管理端策略.md)）：自建统一的织境 Web，
   OpenMetadata 只作后端，OM UI 不修改、不交付（Phase 1 仅实施人员内部使用）。二级侧边栏：新建
   对话、首页（概览、审批中心）、Agent 工作台、探索资产、数据治理、上下文中心。Agent 能力融入
   各页面（全局侧边栏、页面内操作、就地审批、整页工作台），浏览器经 BFF 调用 Omnigent；是否复用
   Omnigent 前端在 003 的 plan 阶段决定。页面随对应特性交付：外壳与公共能力（003）、探索资产
   （018）、本体（011、013）、分类分级（005）、指标与审批（020）、文件（016）、知识包预览与
   Skills（017）、决策轨迹（009）。Phase 1 不做管理端，以配置即代码 + CLI / API 完成（002、
   005），底层组件管理界面仅内部使用；二期建设租户管理与平台运维端两层管理端。
8. **管线编排与数据治理**（已定，见 [ADR-0006](adr/0006-三域数据治理与管线编排.md)）：独立部署的
   Apache Airflow 作为三域管线唯一编排器（不用 OM 内置 Airflow），OM 采集与织境管线统一调度并
   进入 OM 血缘；治理能力按“能力 × 域”划分：OM 能采集的资产复用 OM 的数据质量、自动分类、契约、
   治理工作流，本体层与 OM 看不到的数据自建（014）。

## 5. 特性详情

每个特性给出：要解决的问题、范围、验收标准、宪法关注点，以及可直接粘贴的
`/speckit-specify` 描述。

### 001 工程基座与交付流水线

- **是什么**：开发团队的“地基”，用户看不到，但之后每个特性都在它上面开发：统一的代码仓库结构、新服务的模板、提交代码后自动跑测试和查许可证的流水线（CI），以及一键部署到阿里云测试环境、打包成客户可离线安装的交付包。例：开发者提交代码，流水线自动测试、扫描、部署到测试环境。
- **复用**：Helm（OM、Keycloak、OTel Collector、Langfuse、Apache Airflow 的官方 Chart）、Terraform alicloud provider、kind；SBOM 与扫描工具（Syft / Grype / Trivy、ScanCode，均 Apache 2.0）；CI 平台（plan 中确定）。
- **自建**：monorepo 结构与服务模板、宪法门禁流水线编排、伞形 Chart 与 values 分层、发布验证环境、离线安装包构建。
- **问题**：宪法要求 TDD、契约优先、CI 门禁、客户云可移植交付，开工第一天就要有骨架。
- **范围**：monorepo 骨架与服务模板（含健康检查、OTel、结构化日志、契约测试样例）；
  OTel 关联属性规范（租户、人、Agent、run / session、业务对象、引用的本体与口径，见 ADR-0001）；
  CI：构建、单元 / 契约 / 集成测试、覆盖率 ≥ 80%、静态检查、SBOM、许可与漏洞扫描；
  Helm 伞形 Chart 部署 OM 2.0（server + ingestion + MySQL/PG + OpenSearch + Fuseki）、
  Keycloak、OTel Collector、Langfuse、Doris（含高可用与备份方案）、独立部署的 Apache Airflow
  （KubernetesExecutor）与 DAG 规范（ADR-0006）；Terraform 创建阿里云 ACK / ACR；本地 kind 环境；
  单租户、无阿里云托管服务的发布验证环境；离线安装包构建。
- **验收**：新服务从模板创建到部署进测试环境 < 30 分钟；故意引入的 AGPL 依赖被 CI 拦截；
  同一 Chart 在 kind 与 ACK 均部署成功；离线包可在断网 kind 集群安装。
- **宪法关注点**：II（服务模板）、III（SBOM、许可扫描）、V（OTel）、部署约束全部条款。

### 002 身份、租户与 Agent 委托令牌

- **是什么**：统一的登录与身份能力。每个客户是一个租户，数据互相隔离；人用企业账号登录；Agent 也有自己的身份，代表某个人干活时拿到一张同时写明“哪个人”和“哪个 Agent”的临时通行证（委托令牌）。还包括开通新客户租户的脚本。例：张三登录后让 8D 助手查数据，系统知道是“8D 助手代表张三”在查。
- **复用**：Keycloak：realm / organization、OIDC 登录、令牌交换、client credentials、对接客户 IdP。
- **自建**：Agent 登记模型与登记文件、委托令牌换取流程封装、各服务共用的鉴权中间件（Python 库）、租户开通 CLI、realm 配置即代码、跨租户隔离测试框架。
- **问题**：宪法 IV 要求人与 Agent 各有身份、Agent 携带人的身份、租户来自签名令牌。
- **范围**：Keycloak 每客户一个 realm 或 organization；Agent 身份注册（所属租户、负责人、
  授权范围）；人通过 SSO 登录后为 Agent 换取短期委托令牌（RFC 8693）；无人值守 Agent 的
  服务身份；各服务共用的鉴权中间件（验签、解析人 / Agent / 租户）；跨租户隔离测试框架；
  租户开通 CLI（一次性创建 Keycloak realm、Langfuse project、Doris database 与 workload group、
  OM 隔离配置）；Keycloak realm 配置即代码；Agent 登记文件（YAML，含负责人与授权范围，ADR-0003）。
- **验收**：伪造请求头中的用户 ID 无法通过鉴权；租户 A 令牌访问租户 B 资源 100% 失败；
  人被禁用后其 Agent 在令牌过期内失效；令牌中可区分人与 Agent。
- **宪法关注点**：IV 全部身份条款；部署约束中的多租户条款。

### 005 分类分级、授权求值与审计

- **是什么**：决定“谁能看什么”并记账。给数据打敏感级别标签；每次有人或 Agent 来取数据，按“人的权限、Agent 的授权、数据级别”三者的交集判断能不能给；每次取数都记一笔审计（谁、凭什么授权、拿了什么）。例：8D 助手代表张三查供应商结算价，因数据级别超出 Agent 授权被拒绝，并留下记录。

### 006 统一取数网关

- **是什么**：所有“查实例数据和分析数据”的唯一入口，相当于门禁加安检（ADR-0005）。它不存数据、
  不是数仓，挡在 Doris 本体实例库和客户数仓前面；本体定义和元数据走 OpenMetadata API，不经过它。
  内部 Agent、Notebook、按口径取数、沙箱数据管线直接向它提交 SQL；015 追溯和 018 探索把本体查询
  翻译成 SQL 后也交给它执行。它负责“能不能查、查多少、记下来”，不理解业务含义。例：问数 Agent
  代表张三提交“3 号线一次合格率”的 SQL，网关核对权限后只读执行，限时、限行，返回结果并附上数据来源。
- **复用**：Doris 的 workload group、行策略、只读账号；SQL 解析库 sqlglot（MIT）。
- **自建**：网关服务：授权前置（含按对象类型与属性的列级授权）、只读校验、超时 / 扫描量 / 行数限制、
  临时 schema 生命周期、结果来源与血缘、审计与轨迹；统一的后端接口（SQL 后端为首个实现，为二期
  工具型数据源、IoTDB、Trino 预留）。
- **问题**：内部 Agent、Notebook、问数、追溯与探索都要取数，必须有统一的授权、限流与审计入口；P1 阶段就要用到。
- **范围**：SQL 后端（Doris 本体实例库、客户数仓）；执行前授权求值（人 ∩ Agent ∩ 数据级别，租户
  限定）：本体实例库按对象类型与属性的分级做列级判断，客户数仓按 OM 元数据分类判断；只读执行；
  超时、扫描量与行数上限；Doris 按租户与 Agent 划分 workload group；管线中间结果写入每次运行的
  临时 schema（配额、到期清理）；结果附数据来源与血缘；审计与轨迹；统一后端接口。由已审批指标
  生成 SQL 的能力在 020 中加入；工具型数据源（MCP / CLI / API）在二期接入。
- **验收**：越权查询为零（含列级）；写操作全部被拒绝；大查询不影响其他租户（workload group 隔离
  测试）；临时 schema 到期清理；每次执行有审计与轨迹；P95 延迟目标在 plan 中定。
- **宪法关注点**：IV（授权、只读、审计）；II（独立服务契约）。

```
/speckit-specify 实现统一取数网关：作为查询 Doris 本体实例库与客户数仓的唯一入口，接收内部 Agent、Notebook、指标模型、追溯与探索服务提交的 SQL；执行前按“人 ∩ Agent ∩ 数据级别”在租户内求值，本体实例库按对象类型与属性的分级做列级授权，客户数仓按元数据分类授权；只允许只读查询并设置超时、扫描量与行数上限，在 Doris 中按租户与 Agent 划分 workload group，为数据管线分配带配额、到期清理的临时 schema；返回结果附来源与血缘，记录审计并写入轨迹；执行层采用统一后端接口，为后续接入工具型数据源、时序库与 Trino 预留。

### 007 执行沙箱

- **是什么**：给 Agent 跑代码用的“隔离房间”。Agent 需要运行 Python 或数据处理程序时，在一个临时、隔离的容器里执行：不能直接连数据库（取数只能走网关），只能访问允许的地址，用完即销毁。防止 Agent 生成的代码出错或被诱导时伤到系统。
- **复用**：kubernetes-sigs/agent-sandbox（CRD、预热池）、gVisor / Kata、K8s NetworkPolicy 与 ResourceQuota、Omnigent 沙箱提供者接口。
- **自建**：委托令牌注入、网络策略模板、执行审计与轨迹上报、产出物经对象存储带出、租户隔离配置。
- **问题**：内部 Agent 的大部分场景要运行 Python 与数据处理管线，必须隔离执行（ADR-0002）。
- **范围**：基于 kubernetes-sigs/agent-sandbox 的沙箱，配合 gVisor 或 Kata；预热池；每个会话一个
  有状态沙箱；每次执行注入短期委托令牌，取数一律经 006 统一取数网关，沙箱内不放数据库账号；网络策略
  只放行统一取数网关、对象存储与模型网关；CPU / 内存 / 时长限制；临时文件系统，产出物经对象存储带出；
  执行审计并写入轨迹；作为 Omnigent 的沙箱提供者接入；可在客户 K8s 与离线环境部署。
- **验收**：沙箱内无法直连数据库或访问未放行地址；租户之间沙箱隔离；预热池下冷启动时间目标在
  plan 中定；离线 kind 集群可运行。
- **宪法关注点**：IV（令牌、审计）；III（Apache 2.0 组件）；部署约束（不用云端沙箱服务）。

### 009 决策轨迹与纠正采集

### 017 Context API（OKF 知识包）与 MCP 服务

- **是什么**：数字员工平台从织境拿上下文的“取件窗口”。一次调用返回一个打包好的上下文（知识包），里面只有这个人和 Agent 有权看、且已审批的内容；同时提供 MCP 接口，让各种 Agent 平台按标准协议接入。上下文中心的“知识包预览”和“Skills”页面在这里交付。
- **复用**：OM MCP Server（2.0 默认开启，按调用者权限执行，但只到人）、MCP 官方 Python SDK、OKF v0.2 规范、agentskills.io 技能格式。
- **自建**：OKF 知识包生成（工业 type 词表、指向本体的 resource URI、relations 扩展）、生成前授权求值、按需物化与缓存、本体对象 MCP 工具、Skills 的存放 / 授权 / 版本、“知识包预览”与“Skills”页面。
- **问题**：数字员工平台拿上下文的唯一入口，一次调用返回经策略过滤的上下文包。
- **范围**：OKF v0.2 知识包生成（工业 `type` 词表、指向本体的 `resource` URI、`relations`
  扩展、`sources` / `verified` / `stale_after`）；生成前完成授权求值；按需物化与缓存；
  MCP 服务（复用 OM MCP Server，新增本体对象工具描述，渐进披露）；Skills 存放与授权。
- **验收**：未审批或越权内容不出现在知识包中（测试覆盖）；P1 案例的上下文包覆盖率 ≥ 80%；

### 020 指标语义模型与审批流

- **是什么**：解决“口径谁说了算”。每个指标（如一次合格率）的计算口径、维度、关联关系都有正式定义，提出、评审、生效、废弃都走审批并保留版本；Agent 只能用已审批口径，并按口径自动生成 SQL。数据治理里的“指标”页面和审批中心里的指标审批在这里交付。
- **复用**：OM Metric 实体（表达式、粒度、单位）、OM 治理工作流 / Intake Forms（审批流）。
- **自建**：维度 / 度量 / 关联扩展、口径版本与状态、owner 与审核人路由、接入审批中心、按已审批口径生成 SQL、“指标”页面；MetricFlow 留到二期。
- **问题**：P2 的核心——“口径谁说了算”，Agent 只能用已审批口径。
- **范围**：基于 OM Metric 实体扩展维度、度量、关联；口径的提出、评审、生效、废弃流程与
  版本；指标 owner 与审核人路由；“探索口径”标记；审批状态同步到 Context API；由已审批指标定义生成 SQL，经 006 网关执行，
  结果附口径引用。
- **验收**：首批 ≥ 30 个指标走完审批；同一指标只有一个生效版本；未审批口径被 Agent 使用时
  明确标注。

```
/speckit-specify 实现指标语义模型与审批流：在 OpenMetadata Metric 实体基础上扩展维度、度量与关联，提供口径提出、评审、生效、废弃的流程与版本管理，支持指标 owner 与审核人路由，未审批口径标记为“探索口径”，审批状态同步给 Context API，并由已审批指标定义生成 SQL 交给统一取数网关执行、结果附口径引用，保证 Agent 只使用已审批口径。
```

### 021 帆软报表 SQL 反向解析为指标库

- **是什么**：从客户现有帆软报表的 SQL 里自动反推出第一批指标口径，合并同义指标，作为候选提交审批，省去从零整理指标库；同时统计同一个指标有多少种不同写法。
- **复用**：sqlglot（MIT）解析 SQL；008 运行时上的 Agent 辅助归并同义指标。
- **自建**：帆软报表与数据集读取、口径抽取规则、同义指标合并、候选提交审批、同一指标 SQL 版本数统计。
- **问题**：第一版指标库从现有帆软报表 SQL 反推，也是“自动装配候选语义、人审生效”的首个用例。
- **范围**：解析帆软报表 SQL，抽取口径、维度、过滤条件；同义指标合并候选；生成候选指标进入
  020 审批队列；统计同一指标的 SQL 版本数。

```
/speckit-specify 实现帆软报表 SQL 反向解析：解析现有帆软报表 SQL，抽取指标口径、维度与过滤条件，识别并合并同义指标，生成候选指标提交到指标审批队列，并统计同一指标存在的 SQL 版本数。

## 6. 每个特性的 Spec Kit 流程

每个特性独立一个分支（`NNN-<name>`），按以下顺序推进，一个特性合并后再开依赖它的特性：

| 步骤 | 命令 | 产出 / 检查点 |
| --- | --- | --- |
| 1 | `/speckit-specify <第 5 节的描述>` | `specs/NNN-*/spec.md`：用户故事、需求、可度量的成功标准 |
| 2 | `/speckit-clarify` | 最多 5 个澄清问题，答案写回 spec |
| 3 | `/speckit-checklist` | 按需生成安全 / 多租户 / 许可检查清单（002、003、005、006、007、008、014、017 必做） |
| 4 | `/speckit-plan` | plan.md、data-model.md、contracts/：必须通过 Constitution Check，列出开源服务清单 |
| 5 | architecture-reviewer 评审 | 评 spec 完备性与架构合理性；涉及第 4 节决策的特性必做 |
| 6 | `/speckit-tasks` | tasks.md：按依赖排序，测试任务排在实现任务之前 |
| 7 | `/speckit-analyze` | spec、plan、tasks 一致性检查，问题修完再实现 |
| 8 | `/speckit-implement`（或 TDD 版 `/speckit.tdd-implement`） | 红 → 绿 → 重构，测试先于实现提交 |
| 9 | `/speckit-converge` | 对照 spec 找出未完成项，补为任务并完成 |
| 10 | PR → 评审 → 合并（非 squash） | CI 全绿；评审核对测试先行、契约、许可、租户隔离、权限审计 |

## 7. 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| Doris 承载实例数据的追溯性能与租户隔离 | 015 追溯耗时不达标 | ADR 1 先做 spike：用 004 生成 10⁷–10⁸ 级数据压测追溯 P95，并验证每租户 database + 行策略 |
