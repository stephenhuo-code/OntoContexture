# ADR-0007 租户模型：Phase 1 单租户

- 状态：已接受
- 日期：2026-10-04（2026-10-08 改为 Phase 1 单租户，并按当前架构重写）
- 决策人：@stephenhuo-code
- 影响特性：001、002、005、012、010、014、006、017、019、016、009、020
- 相关宪法条款：IV（只信任签名令牌）、部署约束（Phase 1 例外，宪法 v1.5.0）
- 相关 ADR：ADR-0001、ADR-0004、ADR-0012、ADR-0013

## 背景

最初的设计是阿里云测试环境以一套共享实例支持多个客户（多租户），客户生产环境按单租户运行。评审时确认：
Phase 1 只有一个 POC 客户；OpenMetadata、OpenSearch、Fuseki 都不原生支持多租户，多租户会带来网关租户路由、
OM 域隔离、Omnigent 多租户改造、跨租户测试等大量工作，而 POC 用不上。

## 决策

### 1. Phase 1 单租户

- 一套环境只服务一个客户，该客户可有多个用户与 Agent。测试环境以每套实例服务一个客户（POC 客户或模拟数据）。
  宪法 v1.5.0 部署约束增加相应 Phase 1 例外。
- 租户隔离由部署边界保证（每个客户一套独立部署），Phase 1 不要求跨租户隔离测试。
- **保留 `tenant_id` 字段**：审计、追踪、日志与对象 URI（`urn:ctx:obj:<tenant_id>:...`）中保留 `tenant_id`，取部署
  配置的常量，不来自令牌、不参与路由。将来如需多租户，数据格式不必迁移。

### 2. 各组件在 Phase 1 的做法

| 组件 | Phase 1 |
| --- | --- |
| Keycloak | 一个 realm，不用 Organization；客户 IdP 直接接入该 realm；Agent 为客户端（ADR-0013） |
| AI 网关 | 校验令牌、按工具授权、审计；不做租户路由（ADR-0013） |
| MCP Toolbox | 一个实例、一个 Doris 只读账号 |
| Doris | 一个本体实例库；workload group 按负载类型划分（Agent、页面、管线） |
| OpenMetadata | 不建租户域，不做租户本体分支；客户在标准本体之上扩展自己的本体 |
| Fuseki | OM 自身的 RDF 数据集，无租户划分 |
| Langfuse | 一个 project |
| 对象存储 | 一个 bucket |
| Airflow | 不以租户为参数 |
| Omnigent | 不做多租户改造（ADR-0002 改造项“多租户”暂缓） |
| 公共库 | 不设 `tenancy` 模块；`tenant_id` 由 `config` 提供（ADR-0009） |

## 将来如需多租户：参考设计（暂缓，是否采用另行评估）

是否支持多客户共享实例另行评估，不预设在二期。如需支持，须先修订宪法的 Phase 1 例外，并以下表为起点重新评估：

| 组件 | 可能的隔离方式 | 强制点 |
| --- | --- | --- |
| Keycloak | 单 realm + 每租户一个 Organization；令牌携带由 Organization 映射的租户声明 | Keycloak |
| AI 网关 / MCP Toolbox | 按令牌租户声明路由到该租户的 Toolbox 实例（各用该租户的只读账号） | AI 网关 |
| Doris | 每租户一个 database 与 workload group | Toolbox 的数据库账号 |
| OpenMetadata | 每租户一个 Domain；标准本体为平台共享，租户在自己的分支中扩展；可用 OM 域访问策略 | OM 策略 + `bff` |
| Langfuse | 每租户一个 project | 写入方按租户选择 project |
| 对象存储 | 每租户一个前缀，凭证按前缀授权 | 存储策略 |
| Airflow | DAG 运行以租户为参数；按租户的资源池与连接凭证 | 管线规范 |
| Omnigent | 会话、Agent、沙箱按租户隔离 | Omnigent 补丁 + 扩展 |
| 测试 | 每个对外接口有跨租户隔离测试 | CI |

评估时需重点核实：OM 没有原生多租户，域隔离能否覆盖资产 AI 上下文、上下文中心与内置 MCP；AI 网关按声明路由的能力。

## 理由

- Phase 1 只有一个 POC 客户，单租户去掉了网关租户路由、OM 域隔离、Omnigent 多租户改造与跨租户测试，工作量显著下降。
- 保留 `tenant_id` 字段的成本几乎为零，却避免将来改多租户时迁移审计与追踪数据。

## 考虑过的其他方案

| 方案 | 结论 |
| --- | --- |
| Phase 1 即共享实例多租户（原设计） | 不采用：工作量大，POC 用不上 |
| 每租户一个 Keycloak realm | 不采用：签发者随租户变化，服务需动态信任多签发者（将来多租户时也不建议） |
| 不保留 `tenant_id` | 不采用：将来如需多租户须迁移数据 |
