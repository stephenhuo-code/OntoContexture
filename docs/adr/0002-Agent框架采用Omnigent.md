# ADR-0002 Agent 框架采用 Omnigent

> 特性编号已按 2026-10-31 开发计划迁移表同步；ADR 文档编号不变，已验收规格保留历史编号。

- 状态：已接受
- 日期：2026-10-03
- 当前交付分工：2026-10-31 分期 + 2026-11-01 方案 B 扩展边界（007 身份与会话集成；012 运行时、基础沙箱与加固）
- 决策人：@stephenhuo-code
- 影响特性：001、002、004、009、012、022、028、007，二期自演进
- 相关宪法条款：II（服务边界）、III（开源许可、不长期深度分叉）、IV（身份与授权）、V（可观测性）
- 相关 ADR：ADR-0001（轨迹与运行状态存储）

## 背景

织境有两类 Agent：

- **客户侧 Agent**：作为织境的客户端，调用 MCP / Context API，验证身份与权限契约（028、022 的参考实现）。
- **织境内部 Agent**：织境自身的 Agent 能力。大部分场景需要真正执行 SQL 或数据处理管线
  （探索取数、口径校验、映射验证、数据质量检查、自演进分析），可能是多 Agent 系统，
  需要会话管理、并发、隔离执行与界面。

评估过的框架：Pydantic AI（MIT，轻量库，原生 OTel 与持久化执行对接，但会话、沙箱、界面需自建）、
Omnigent（Apache 2.0，工程化完整）、OmniAgent（GPL-3.0，排除）、Multica（附加条件限制嵌入与对外
托管，排除）、LangGraph（团队决定不用）。

## 决策

客户侧 Agent 与织境内部 Agent **统一采用 [Omnigent](https://github.com/omnigent-ai/omnigent)**。
团队熟悉其架构与界面，缺失能力由团队按需改造。

选择理由：Omnigent 已实现大量工程化能力——会话与服务端、YAML 定义 Agent 与子 Agent、MCP 工具、
策略（审批、工具调用次数、成本上限）、OIDC 登录、Web 界面、定时任务、以及沙箱提供者
（含 Kubernetes 与 [kubernetes-sigs/agent-sandbox](https://github.com/kubernetes-sigs/agent-sandbox)
及预热池）。这些用 Pydantic AI 都需要自建。

### 执行

- **取数与调模型**：一律经 AI 网关（009，ADR-0013）：取数走 MCP Toolbox（只读账号、超时与行数上限、审计），
  模型走 AI 网关的模型网关。
- **（已被 2026-10-23 修订取代）Phase 1 不做执行沙箱**：内部 Agent 只开放 MCP 工具，不开放 shell 与代码执行；Omnigent 运行在普通 Pod 中，
  不持有数据库账号与厂商 key，网络策略只放行 AI 网关。数据处理由 Airflow 管线完成，不由 Agent 临时执行代码。
- 当前执行沙箱统一在 012 评估并交付（候选 agent-sandbox + gVisor / Kata，经 Omnigent 官方提供者接入）；
  云端沙箱服务（Modal、Daytona、E2B Cloud 等）不得用于交付。

### 需要改造或验证的能力

| # | 能力 | 现状（v0.16.0） | 处理 |
| --- | --- | --- | --- |
| 1 | 持久化执行 | 回合与 steering 状态只在 runner 进程内存（`omnigent/runner/app.py`），重启即丢；上游已移除 DBOS 设计 | 改造：按 ADR-0001 写 rollout 到 PostgreSQL，支持等待审批与重启后恢复 |
| 2 | 委托令牌透传 | 支持 OIDC 登录其界面；会话调用 MCP 时携带当前用户令牌未见文档 | 改造：以 Agent 的 Keycloak 客户端身份做标准令牌交换（ADR-0013），每个会话与每次 MCP 调用携带该令牌；恢复时重新交换 |
| 3 | 多租户 | 有用户与邀请制，无租户概念 | 暂缓：Phase 1 单租户（ADR-0007），是否多租户另行评估 |
| 4 | OTel 轨迹 | 文档未提 OpenTelemetry；自带匿名使用遥测 | 改造：以 OTLP 输出到 Collector，带 ADR-0001 规定的关联属性；**关闭对外遥测** |
| 5 | 并发规模 | 运行状态在进程内存，设计目标为团队协作 | 验证：Phase 1 压测 500 个并发运行；不足时改造 runner 水平扩展 |
| 6 | 离线与私有化模型 | 支持 OpenAI / Anthropic 兼容网关接 vLLM、Ollama 等 | 验证：断网环境 + 私有化模型跑通；选定内部 Agent 使用的执行器（harness），须支持私有化模型 |
| 7 | 界面融合 | Omnigent 自有完整 Web 应用 | 当前方案：织境自建轻量页面助手，完整工作台官方嵌入；经 BFF 共享服务端会话（ADR-0003 2026-11-01 修订） |
| 8 | 版本与升级 | 0.x，约每周发版 | 锁定版本；每次升级跑完整回归后再跟进 |

### 改造方式（宪法 VI）

- 优先级：① 用 Omnigent 的扩展点（`omnigent.sandbox_providers` 入口、extensions、策略、YAML）；
  ② 向上游提 issue / PR；③ 补丁。
- 补丁采用**上游镜像仓库**方式（宪法 VI 第 2 种，与 OM 一致，ADR-0011）：织境维护的 Omnigent 仓库以子仓库挂在
  `third_party/omnigent/src/`（见文末 2026-10-16 修订）；主分支只同步上游，改动只放在发布分支 `ctx/<上游版本>`；每个提交在
  `third_party/omnigent/PATCHES.md` 登记（目的、上游 issue / PR、能否随升级删除）；CI 核对发布分支与上游标签
  的差异与登记表一致。
- 补丁只为上游增加扩展缝隙，功能实现在 `extensions/omnigent-plugins`。若某项改造（尤其 #1 持久化）上游不接受
  且改动持续增大，或连续两次升级冲突，MUST 重新评估本 ADR。

## 影响

正面：
- 会话、策略、定时任务直接复用，内部 Agent 与客户侧 Agent 用同一套运行时。
- 团队熟悉架构，改造可控。

负面与代价：
- 持久化、委托令牌、OTel 与执行集成的缺口须按锁定版本复核；可能需要运行时扩展或最小补丁，产生升级回归成本。
  不预设全部改造都落入核心源码；多租户已暂缓，见 2026-10-08 修订。
- 依赖 0.x 项目，接口变动频繁。
- 取数入口（AI 网关）与权限与框架无关，由织境集成与配置。

## 考虑过的其他方案

| 方案 | 结论 |
| --- | --- |
| 内部 Agent 用 Pydantic AI | 不采用：会话、沙箱、界面、策略需自建，工程量大于改造 Omnigent |
| 内部 Pydantic AI + 外部 Omnigent 两套 | 不采用：维护两套运行时 |
| OmniAgent | 排除：GPL-3.0 |
| Multica | 排除：附加条件禁止嵌入商业产品与对外托管（含测试环境给客户使用） |
| LangGraph | 团队决定不用 |

## 修订（2026-10-23）：Phase 1 开放终端与代码执行，经执行沙箱

- **背景**：织境 Web 以官方嵌入入口集成完整的 Omnigent 工作台（ADR-0003 2026-10-23 修订）。数据工程师开发数据管线、与 Airflow
  交互需要工作台的终端与代码执行。Omnigent 的架构为“服务端 + 执行端（runner）”：终端、代码与工具都在执行端运行，服务端不执行
  Agent 代码；执行端除在用户本机运行外，官方支持放入沙箱，含 Kubernetes 方案（`deploy/kubernetes`，对接 kubernetes-sigs/agent-sandbox
  与 NVIDIA OpenShell）。
- **决策**（负责人，2026-10-23）：Phase 1 对数据工程师开放终端与代码执行，执行端一律运行在集群内的执行沙箱中，经 Omnigent 官方支持的
  沙箱方式接入，不自建沙箱：
  - 沙箱候选为 kubernetes-sigs/agent-sandbox，隔离运行时（gVisor / Kata）、许可与资源需求在 012 的 plan 中确认（2026-10-31 修订）；云端沙箱服务
    （Modal、Daytona、E2B Cloud 等）仍不得用于交付。
  - 沙箱只持有当前用户的委托令牌（`sub` 为人），权限不超过该用户（宪法 IV）；网络策略只放行 AI 网关、Airflow 等登记的目标；
    命令与执行过程进入审计与轨迹。
  - 原分工（已被 2026-10-31 修订取代）：004 部署基础执行沙箱；012 加固。当前以文末修订为准。
- **影响**：取代“Phase 1 不做执行沙箱，内部 Agent 只开放 MCP 工具”；ADR-0005 中 CLI 在沙箱中执行的二期安排不变（工具型数据源）。

## 修订（2026-10-31）：拆分界面集成与运行时，沙箱统一在 012 交付

- **背景**：原 004 同时承担外壳、资产目录、审批、Omnigent 嵌入与沙箱，验收耦合过大；负责人决定拆分独立 spec。
- **分工**：004 只交付外壳与设计系统，并提前做嵌入兼容性 spike；007 交付基础 Omnigent 服务部署、官方嵌入工作台、
  BFF 代理、用户身份与会话级 MCP、页面助手上下文及同会话延续。007 的接口必须完成服务端鉴权，令牌不交给浏览器。
- **执行边界**：007 关闭终端、代码执行及定时执行入口；不以尚未加固的执行环境作为界面集成的前提。
  012 统一交付基础执行沙箱和安全加固，包括官方 Kubernetes 沙箱接入、隔离运行时选择、按人隔离、网络白名单、
  资源配额、命令审计与恢复，并验收数据工程师终端和代码执行后开放入口。
- **运行时边界**：012 继续承担 rollout 持久化、委托令牌续期 / 恢复、经 AI 网关取数与调模型、OTel、离线与并发验证；
  依赖 009 与 007。优先官方扩展点，必须补丁时遵循宪法 VI。
- **替代关系**：取代 2026-10-23 修订中的“004 基础沙箱、012 加固”分工；Phase 1 最终提供沙箱内代码执行的目标不变。
  ADR-0005 的工具型 CLI 数据源范围不变；不增加自建微服务。

## 修订（2026-11-01）：方案 B 的运行时与受控二次开发

- **决策**：采用 ADR-0003 的方案 B。主界面归织境，完整工作台使用官方嵌入，运行时继续复用 Omnigent；
  嵌入选择不取消必要的运行时二次开发，也不意味着 UI 或身份集成零成本。
- **维护范围**：007 可为签名身份、受控会话接口及能力限制评估扩展；012 负责持久化、委托令牌续期 / 恢复、OTel 与执行沙箱。
  前后端都遵循配置 → 官方扩展点 → 最小补丁；功能放独立扩展包，补丁主要补充接口，不把业务页面写进上游核心。
  每个实际补丁仍须上游优先、发布分支维护和 `PATCHES.md` 登记；本次没有新增或实施补丁。
- **官方客户端**：页面助手经 BFF 优先复用 `omnigent-client`，锁定版本与服务端一致。v0.18.0 客户端依赖同版
  `omnigent` 包，007 在引入前检查依赖体积、许可证与构建兼容；不复制 SDK 或直接依赖私有聊天状态。
  工作台与助手关联同一服务端会话 ID，真实互通仍需验证。
- **用户识别**：v0.18.0 的 OIDC / accounts Bearer 校验是其自身 HS256 会话令牌，不是通用 Keycloak 访问令牌校验。
  `AuthProvider` 与 `create_app(auth_provider=...)` 提供自定义身份接缝，优先验证通过独立扩展校验受信 IdP 签名、
  受众与有效期；不能把接缝存在当作生产启动接线已完成。BFF 剥离浏览器身份头，上游落实会话权限。
- **委托链路**：Omnigent 用户识别与 Agent 访问网关的身份分别验证；后者保留签名的 `sub = 人`、`azp = Agent` 和受众限制。
  会话 MCP 配置会把 headers 持久化到 Agent 包，写入 Authorization 不构成动态令牌方案；007 须明确凭证注入与失效行为，
  不用静态配置长期保存访问令牌，不允许过期令牌继续调用。012 完成续期、执行恢复后的重新交换与审计加固。
- **能力分期**：007 在服务端拒绝未交付的终端、代码和定时执行能力，界面关闭只作配套；`sidebarConfig` / CSS 不属于授权。
  012 安全沙箱验收后再开放执行入口。
- **证据与状态**：依据锁定提交 `a8676d23e88df7918f4f8ef1c7c4e3186e710354` 的静态源码；
  具体路径与待实测项目见 [004 research](../../specs/004-web-shell/research.md) 和
  [嵌入验证契约](../../specs/004-web-shell/contracts/embed-readiness.md)。真实身份桥接、SDK 互通和委托生命周期尚未验证通过。
