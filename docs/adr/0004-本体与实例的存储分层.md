# ADR-0004 本体与实例的存储分层

- 状态：已接受
- 日期：2026-10-04
- 决策人：@stephenhuo-code
- 影响特性：001、002、005、006、010、011、012、013、015、017、018
- 相关宪法条款：II（服务独占数据存储、契约优先）、III（开源许可）、IV（租户隔离）、部署约束
- 相关文档：产品规划第 4 节（工业本体四层）、第 5 节（技术选型要点）

## 背景

工业本体分为定义与实例两层（计划术语表）：

- **本体定义**：对象类型、关系类型、属性、术语，规模为几十个对象类型、几百到几千个术语。
- **本体实例**：按对象类型存入的具体数据，包括主数据（设备、产线、工位、物料、供应商、人员，
  规模 10³–10⁵）和业务流水（批次、工单、工序报工、检验记录、NCR，工单约 10⁷ / 年、检验记录约
  10⁸）。

OpenMetadata 管理的是元数据（表、字段、血缘、术语、域等），本身没有主数据管理；其实体存储
（MySQL / PG + OpenSearch，每个实体为带版本与变更事件的 JSON）面向元数据规模设计，RDF（Jena
Fuseki）目前为 Beta。产品规划原写法为“一期设备、点位仅作为元数据实体入 OM”。

需要决定主数据实例放在哪里，这决定本体实例集中在一个库还是分散在两个库。

| 方案 | 本体定义 | 主数据实例 | 业务流水实例 | 结论 |
| --- | --- | --- | --- | --- |
| **A** | OM | Doris | Doris | **采用** |
| B | OM | OM（作为 OM 实体） | Doris | 否决：实例分散在两个库，P1 追溯需跨库关联；需维护两条接入管线；主数据塞入目录使 OM 膨胀，而 Phase 1 只读、主数据由源系统治理，OM 治理能力用处不大 |
| C | OM | OM | OM | 否决：OM 无法承载 10⁸ 级实例 |
| D | 图数据库 | 图数据库 | 图数据库 | 推迟：定义与实例同库，但需另行打通 OM 的治理能力；作为二期属性图选型时的评估方向 |

## 决策

### 1. 按层分库

| 层 | 存储 | 内容 |
| --- | --- | --- |
| 本体定义与元数据 | **OpenMetadata**（实体存储 + Jena Fuseki 中的 RDF） | 对象类型、关系类型、属性、术语；源系统的表、字段、血缘；源表字段 → 对象属性的映射；OT 点位定义（二期） |
| 本体实例 | **Doris（本体实例库）** | 全部对象实例（主数据与业务流水）及关系实例 |
| 时序数值 | Apache IoTDB（二期） | 点位的时序数据 |

- 每一层只有一个权威来源：Doris MUST NOT 存储类型与术语的定义；OM MUST NOT 存储对象实例；
  Fuseki 只存本体与元数据的 RDF，MUST NOT 存实例。
- 本体实例库不替代客户数仓：客户的分析数据仍在客户数仓中，本体实例库只存按本体组织、服务追溯
  与三域图谱的数据（Phase 1 为近 6–12 个月）。

### 2. Doris 的表结构由本体生成

- 每个对象类型对应一张对象表，每个关系类型对应一张关系边表；表结构由 011 根据本体定义与映射生成，
  不手工建表。
- 本体变更（如新增属性）随本体版本生成 Doris 迁移脚本，经评审后执行；迁移 MUST 可回退。
- 对象表每行 MUST 携带对象类型 URI 与对象 URI；关系边表每行 MUST 携带关系类型 URI、起点与终点
  对象 URI、数据来源与时间。URI 规则在 011 中定义，并与 Context API 中 OKF 的 `resource` URI
  保持一致（017）。
- 租户隔离：每个租户一个 Doris database，配合行策略（ADR-0003、宪法 IV）。

### 3. 逻辑上一张图

- 通过 URI 把 OM 中的定义与 Doris 中的实例关联起来；对外由追溯查询服务（015）与探索资产（018）
  呈现为一张图，调用方不感知两个库。
- 所有对实例的访问经统一取数网关（006，见 ADR-0005）。
- 本体实例如何进入搜索索引，在 018 的 plan 中确定。

### 4. 人员实例与平台用户分开

- **人员实例**：员工、班组成员等，来自飞书组织架构或 HR，存于 Doris，参与追溯（如责任班组）。
- **平台用户**：能登录织境的账号，在 Keycloak 中。
- 两者通过工号或飞书用户 ID 关联：授权依据 Keycloak 中的身份与角色，业务角色（岗位、班组）来自
  人员实例。

### 5. 与产品规划的差异

产品规划“一期设备、点位仅作为元数据实体入 OM”改为：**设备是对象实例，存于 Doris；点位定义是
元数据，存于 OM**（OT 接入与点位时序为二期）。

## 影响

正面：
- P1 追溯链路（NCR → 批次 → 工单 → 工序 → 设备 → 班组）全部在 Doris 内关联完成。
- 只有一条实例接入管线（012）。
- OM 保持数据目录的定位，不因主数据膨胀。
- 二期属性图只需从 Doris 一个来源同步。

负面与代价：
- Doris 成为核心存储，客户生产环境需要其高可用、备份与恢复方案，并进入 Helm 与离线安装包（001）。
- 需要“本体 → Doris 表结构”的生成与迁移工具（011）。
- 主数据的质量与治理依赖客户源系统，织境 Phase 1 只读。
- “一张图”的一致性由 015 / 018 的服务层保证，而不是单一存储。

## 后续工作

- 001：Doris 纳入 Helm 与离线安装包，含高可用与备份方案。
- 002：人员实例与 Keycloak 用户的关联方式。
- 011：URI 规则；由本体生成 Doris 表结构与迁移脚本。
- 012：接入管线覆盖主数据与业务流水，统一写入 Doris。
- 015 / 018：基于 URI 的逻辑图查询；本体实例的搜索索引方案。
- 追溯性能 spike：用 004 的模拟数据在 10⁷–10⁸ 规模下压测追溯 P95，验证每租户 database + 行策略。
