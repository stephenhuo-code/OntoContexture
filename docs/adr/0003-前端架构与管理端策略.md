## 背景

织境需要一套面向客户的界面。可复用的现成界面有两套：

- **OpenMetadata UI**：数据目录功能完整（搜索、资产详情页、血缘、数据质量、术语、治理），但
  `openmetadata-ui` 采用 Collate Community License 1.0：允许修改与分发，须显著标注修改、保留
  Collate 版权声明并附许可声明，不授予商标权，禁止提供与 Collate 竞争的在线服务。技术栈为
  React 18、react-router 7、Ant Design 4（全局样式）、Tailwind 4。
- **Omnigent Web**：Apache 2.0，技术栈为 React 18、react-router 7、Vite、Tailwind 4、
  shadcn / Radix、TanStack Query（manifest 列有 Ant Design 6，锁定源码的界面未使用）。官方提供嵌入入口（`web/src/embed.tsx` 导出
  `OmnigentApp`），可挂载到宿主应用的 React 树与路由中，样式限定在自身范围。

初版评估过的方案（本表 A 指 OM UI；2026-11-01 对 Omnigent 主应用 / 嵌入的两方案比较见文末）：

| 方案 | 结论 |
| --- | --- |
| A. 改造 OM UI 作为产品主界面，嵌入 Omnigent | 否决：等于长期维护大型前端分叉（违反宪法 VI），OM 2.0 刚重构界面、2.1 仍将大改；信息架构以数据目录为中心，不适合织境；Ant Design 4 全局样式与 Omnigent 的 Ant Design 6 可能冲突；受 CCL 约束，以后无法提供在线服务 |
| B. 自建统一界面，OM 只作后端 | **采用** |
| C. 自有控制台 + 嵌入 Omnigent，OM UI 作为并列的管理工具 | 否决：多套界面拼接，不像成熟产品 |

## 决策

### 1. 自建统一的织境 Web，OpenMetadata 只作后端

- 客户只看到织境 Web（加上飞书中的数字员工交互）。OpenMetadata 通过其服务端 REST API 使用
  （Apache 2.0）；`openmetadata-ui` MUST NOT 修改、MUST NOT 交付给客户。
- Phase 1 期间 OM UI 仅供我们的实施人员内部使用；织境 Web 覆盖相应功能后停用。
- 浏览器只调用织境自己的后端接口（FastAPI），MUST NOT 直接调用 OpenMetadata、Langfuse、
  Keycloak 管理接口、Omnigent 等底层服务（Omnigent 经 BFF 代理，见决策 3）；授权在服务端完成（宪法 IV）。
- 登录采用 Keycloak OIDC（授权码 + PKCE），令牌交给后端，复用 001 的鉴权与 BFF 会话；004 补充 Web 准入与独立退出规则。
- 2026-11-03 修订：用户主动登录（含退出后登录、失败恢复）由 BFF 固定携带 `prompt=login`，要求 Keycloak 重新认证；有效会话的刷新 / 续期继续保持。退出只删除织境会话，不调用 IdP logout，不主动注销其他客户端。

### 2. 技术栈与 Omnigent Web 保持一致

- React 18、TypeScript、Vite、Tailwind 4、shadcn / Radix、TanStack Query、react-router 7；
  图形（血缘、本体、追溯路径）使用 `@xyflow/react`。
- MUST NOT 引入与 Omnigent Web 冲突的 UI 库版本（例如 Ant Design 4）；完整工作台通过 `OmnigentApp` 集成，
  共享 React / Router 版本以锁定源码与实际兼容性验证为准，不复制其内部组件。
- 织境自有设计系统与品牌：组件库放在 monorepo 的前端包中；支持明暗主题；界面语言先做简体中文，
  文案集中管理以便后续增加英文。

### 3. Agent 能力融入各页面

Agent 的使用与数据目录、治理、上下文深度结合，不做成一个孤立的嵌入页面。

| 融合方式 | 场景 |
| --- | --- |
| 全局 Agent 侧边栏 | 织境自建轻量页面助手；切换页面可延续会话，每条消息绑定发送时的页面上下文，不改写历史 |
| 页面内 Agent 操作 | 对象详情页“找相关 NCR”、血缘图“影响分析”、指标审批“对比口径差异 / 检查 SQL”、轨迹“分析这次纠正”，结果渲染在当前页面 |
| 就地审批与确认 | Agent 的审批请求转为业务页面中的确认组件，不跳回对话界面 |
| Agent 工作台（整页） | 007 通过 OmnigentApp 嵌入完整工作台，与页面助手延续同一服务端会话；终端与代码执行在 012 安全沙箱验收后开放 |

- **结果类型契约**：Agent 的输出不只是文字。定义“织境结果类型”（表格、血缘 / 追溯子图、对象
  卡片、口径差异等），由工具调用返回结构化数据，前端用织境组件渲染；结果中的对象可跳转到其
  详情页，形成页面与 Agent 的双向联动。
- **调用链路**：前端 → 织境后端（BFF）→ Omnigent 官方 API / SDK。完整工作台的 HTTP、SSE、WebSocket
  经 BFF 转发；页面助手经 BFF 适配官方客户端。会话级 OM MCP 经 AI 网关接入，不另建织境 MCP 服务。
- **身份边界**：BFF 复用已验证身份，剥离浏览器提供的身份头；Omnigent 用户识别与 Agent 调用下游的委托令牌
  分别验证，不能假设转发 Keycloak Bearer 即可。委托身份、受众与令牌生命周期按 ADR-0002、0013 处理。
- **前端复用已确定**：完整工作台官方嵌入，页面助手与业务结果组件由织境维护；具体边界见 2026-11-01 修订。
  004 验证宿主构建 / 挂载及代理 / 身份方案依据，007 在计划与工期定稿前验证真实身份、上下文和同会话延续。

### 4. 信息架构：二级侧边栏

一级为图标导航，二级为对应模块的菜单面板。Phase 1 交付的二级菜单加粗。

| 一级 | 二级 | 交付特性 |
| --- | --- | --- |
| 新建对话 | 快捷发起对话；下方显示最近对话 | 004 入口、007 会话 |
| 首页 | **概览**（三域覆盖、已审批口径、Agent 调用量、纠正率）、**审批中心**（我的待办） | 004 布局、008 待办；业务指标随 010、005、015 |
| Agent 工作台 | **Agent 列表**、**按 Agent 发起主对话**、多 Agent 协作会话、会话历史 | 007 界面集成、012 运行时与执行沙箱 |
| 资产搜索（原“探索资产”） | **全局搜索**、按域浏览、**对象详情**（含关系、血缘、**追溯图**、相关轨迹） | 006（承接原资产目录）、027、024、026 |
| 数据治理 | **本体**（类型、关系、映射、领域包、提案）、**术语库**、**分类分级**、**指标**（口径与版本）、访问策略、审计报告、工作流 | 016、018、015 |
| 上下文中心 | **概览**、**文件**、文章、记忆、**Skills**、**知识包预览**、**决策轨迹**、归档 | 023、017、010（随后续特性加入导航） |
| 底部 | 收件箱、个人设置；二期增加“管理” | — |

Notebook（020）作为探索工作入口，JupyterLab 的嵌入方式在 020 的 plan 中确定。
各业务页面随对应特性交付，004 织境 Web 外壳只提供外壳、导航、设计系统与公共能力。

**防重复规则**

1. **同一对象只有一个详情页。** 资产搜索负责“找、看、用”（全局搜索、筛选、浏览、发起 Agent
   对话），数据治理负责“定义、维护、审批”（编辑、批量操作、工作流、策略）。探索只做列表与搜索并
   链接到详情页，治理的编辑与流程也落在同一详情页上。
2. **探索覆盖三域，含实例。** 除元数据（表、指标、报表）外，探索可直接搜索本体对象实例（设备、
   批次、工单、NCR）与工作数据（人员、岗位、飞书讨论）。
3. **审批只有一套。** 首页审批中心是按“人”的视角（我的待办，汇总口径、本体提案、知识片、记忆、
   Agent 写回等审批）；数据治理中只看各类对象的审批流程配置与历史。同一份数据，两种视角。
4. **上下文中心回答“Agent 能看到什么”。** 其中的审批动作统一进入审批中心。

**上下文中心的内容**

| 内容 | 说明 | Phase 1 |
| --- | --- | --- |
| 文件 | SOP、控制计划、历史 8D、检验标准等；来源为手工上传与连接器同步（飞书云文档、企业文档库）。拆为知识片，每个知识片带审批状态（OKF `verified`）、来源与时效，继承文件的分类分级；只有已审批的知识片进入知识包 | ✓ |
| 文章 | 人写的长文，有版本（口径说明、处置规范、业务背景） | 二期 |
| 记忆 | 从对话沉淀的原子事实，带时效与来源，经审批生效 | 二期（产品路标中记忆审批属阶段二） |
| Skills | Skills 的存放、授权与版本 | ✓ |
| 知识包预览 | 选择入口对象（如 NCR）与身份（人 + Agent），展示 Context API 将返回的 OKF 知识包：包含的条目及其审批状态、版本、来源、时效，以及被过滤的条目和原因（数据级别、未审批）。用于上下文覆盖率验收、权限验证、口径 owner 自查 | ✓ |
| 决策轨迹 | 每次 Agent 调用的完整记录（数据来自 Langfuse，经织境服务授权后展示）：触发、身份、使用的上下文及版本、工具调用、输出、人工修订前后对比、采纳 / 驳回与理由；可按 NCR / 人 / Agent / 时间筛选；可加入纠正样本；可“用当时身份重新预览知识包”对比当时与现在 | ✓ |
| 归档 | 已废弃的文件、文章与记忆 | 随文件 |

### 5. 管理端策略

**Phase 1 不建设管理端。** 管理工作以“配置即代码 + CLI / API”完成，底层组件的管理界面只作
查看与排障：

| 管理事项 | Phase 1 做法 |
| --- | --- |
| 租户开通 / 停用 | 租户开通 CLI：一次性创建 Keycloak realm、Langfuse project、Doris database 与 workload group、OM 隔离配置（002） |
| 用户与角色 | Keycloak（或对接客户 IdP）；realm 配置导出为文件入 Git，变更走 PR（002） |
| Agent 注册与授权范围 | Keycloak client + Agent 登记文件（YAML，含负责人与授权范围）入 Git（002） |
| 数据分类分级 | 织境 Web 分类分级页面（016） |
| 数据源与飞书连接 | OM Ingestion 配置与 Helm values 入 Git；凭证存 K8s Secret / KMS（005、014） |
| 审批路由 | 配置文件入 Git（015） |
| 配额、模型网关 | Helm values、AI 网关配置与 K8s 资源（001、009、012） |
| Omnigent Agent 定义与策略 | YAML 入 Git；底层管理入口仅内部，织境内嵌工作台按 007 / 012 的授权边界交付 |
| 审计查询 | 按 trace_id 查询 AI 网关与数据库审计（009） |
| 轨迹排查 | Langfuse 界面（仅内部）（010） |

约束：

- 底层管理界面（Keycloak、OM UI、Langfuse、Omnigent 管理入口）只对内部开放：限制访问网段、使用独立
  管理员账号，MUST NOT 交给客户使用；织境内嵌的 Agent 工作台属于产品功能，权限由 BFF 与上游服务端共同执行。
- 管理操作可追溯：走 Git 的以 PR 记录为准；直接在界面操作的依赖组件自身日志（Keycloak 管理
  事件；OM 活动记录需确认覆盖范围；Langfuse 开源版无审计日志，只看不改）。
- 所有配置能力先以 API / CLI 提供，二期管理端直接复用，不返工。

**二期建设两层管理端**，与织境 Web 同一代码仓库与设计系统：

| | 租户管理 | 平台运维端 |
| --- | --- | --- |
| 使用者 | 客户企业管理员 | 我们（测试环境）、客户 IT 运维（私有化部署） |
| 入口 | 织境 Web 内的“管理”区域，按角色显示 | 独立入口，建议限制访问网段 |
| 内容 | 用户与角色、Agent 与授权、分类分级与策略、数据源与飞书连接、审批路由、租户配额、审计、轨迹保留 | 租户开通与停用、配额、系统健康、版本与升级、模型网关、Omnigent 运行时、跨租户审计 |
| 身份 | 租户内管理员角色 | 独立的平台运维身份，所有操作强制审计 |

平台运维端随私有化交付包一起交付。

## 影响

正面：
- 产品信息架构、品牌与视觉统一，围绕织境的核心概念（三域图谱、本体、审批、Agent）设计。
- 许可边界清晰：前端代码为自有，OM UI 不修改不交付，不受 CCL 约束，保留以后提供在线服务的可能。
- Agent 能力融入探索、治理、上下文各页面，体验连贯；信息架构不依赖是否复用 Omnigent 前端。
- 与 Omnigent Web 对齐共享依赖，复用完整工作台。
- Phase 1 不做管理端，集中投入业务界面。

负面与代价：
- 数据目录子集、轻量页面助手、页面内 Agent 操作与结果渲染组件需要自建；初版人员 / 周期估算不再作为当前排期依据，
  以开发计划的分期基线和 spike 后复估为准，007 的 1.5 周为暂估。
- 嵌入仍依赖上游接口、共享 React / Router 与构建产物兼容性；同会话交互、中文化和深度样式定制不因嵌入自动完成。
- Phase 1 管理工作依赖实施人员熟悉多个底层组件与配置文件。

## 修订（2026-10-07，见 ADR-0012）

- Phase 1 自建服务只有 `bff`（ADR-0013 取消了 `sql-gateway`）；浏览器仍只访问 `bff`，页面取数由 `bff` 经 AI 网关完成。
- Agent 取上下文使用 OM 内置 MCP 服务与资产 AI 上下文，不建织境自有的 MCP 服务；`bff` 为 Omnigent 会话挂载的是 OM 的 MCP 服务。
- 上下文中心的“文件”“知识包预览”使用 OM 上下文中心与资产 AI 上下文；“决策轨迹”页面经 `bff` 读取 Langfuse。

## 修订（2026-10-08）：前端的部署方式

- 织境 Web（`apps/web/`）打包为静态资源镜像，由 nginx（BSD-2-Clause）提供，作为独立部署单元 `web`；Envoy Gateway
  把页面请求路由到 `web`，把 `/bff/*` 路由到 `bff`。前后端各自发布、各自回滚。
- 浏览器中的页面只调用 `bff`，不直连任何底层服务（不变）。

## 修订（2026-10-16）：两类用户与前端复用

- **两类用户**：最终用户（业务人员）在 Paperclip 中与数字员工对话（ADR-0010）；数据处理与治理人员使用织境 Web。
- **织境 Web 即重做的 OM 界面**：面向数据处理与治理人员，OM 只作后端（本 ADR 方案 B 不变），OM 界面仍不交付给客户。
- **历史决定，已被 2026-10-23 修订取代**：当时拟复制 Omnigent 前端组件到 `apps/web/` 深度改造，并手动合入上游更新。
  该方案不再执行；当前采用官方嵌入与独立业务组件，维护边界见 2026-11-01 修订。

## 修订（2026-10-23）：以官方嵌入入口集成 Omnigent Web

取代 2026-10-16 修订中“复制 Omnigent 前端组件到 `apps/web/` 并深度改造”的做法。
本节保留当时的决策记录；配置能力、页面助手形式和身份接入假设已由 2026-11-01 修订收紧，不能按旧假设实施。

- **背景**：核查 v0.18.0 的 Omnigent Web：约 1,205 个 TS / TSX 文件、36.5 万行，是完整的 Agent 工作台（对话、终端、代码编辑、
  文件、目标、定时任务等）。负责人确认这些能力在织境中大多会用到，尤其是数据管线开发与 Airflow 交互。复制后深度改造等于长期维护
  一个大型分叉（违背宪法 VI）；只取对话组件又会丢掉这些能力。Omnigent Web 官方提供嵌入入口 `OmnigentApp`（`src/embed.tsx`，
  为宿主应用嵌入完整工作台而设计）：宿主注入接口调用方式与 WebSocket 地址、挂载在宿主路由的子路径下、样式限定在 `.omnigent-app`
  范围内、明暗与调色板由宿主控制、提供侧边栏配置与扩展机制。界面实际基于 shadcn / Radix / Tailwind（`package.json` 列有 antd，
  但源码未使用），与织境技术栈一致。
- **决策**：织境 Web 自建外壳（二级侧边栏与信息架构、设计系统、首页概览、审批中心及之后的治理、探索、上下文中心等页面），
  “新建对话”“Agent 工作台”及数据开发工作区以官方嵌入入口 `OmnigentApp` 集成完整的 Omnigent 工作台：
  - **配置假设已更正（2026-11-01）**：当时拟用嵌入配置统一品牌、主题、路由和侧栏；实际需区分服务端 branding、
    宿主参数与有限的侧栏策略。必要修改按宪法 VI 评估扩展和登记补丁，不作零源码改动承诺。
  - 全部接口请求与 WebSocket 经 `bff` 转发。**身份假设已收紧（2026-11-01）**：注入委托令牌不等于上游用户识别已解决，
    需要单独验证签名身份桥接与下游委托链路。
  - **侧栏形式已取代（2026-11-01）**：当时拟用侧滑或跳转打开完整嵌入工作台；当前页面助手由织境实现，完整工作台整页嵌入，
    两者关联同一服务端会话，上下文由 BFF / 官方会话接口适配。
  - 织境 Web 与 Omnigent Web 共用同一个 React 与路由库：织境 Web 对齐到 React 18、react-router-dom 7（随 Omnigent 版本调整）。
  - Omnigent Web 的嵌入产物由 `third_party/omnigent/src/` 锁定版本构建，随子仓库版本升级。
- **原影响（部署分工已由 2026-10-31 修订取代）**：Omnigent 的部署（不改造）曾随 004 提前；改造（持久化、委托令牌、OTel、经 AI 网关取数与
  调用模型）仍在 012。`apps/web/THIRD_PARTY.md` 不再需要记录复制的代码。
- **风险与 004 spike 验证项**：官方嵌入构建面向 rspack 宿主，需验证在 Vite 宿主中可用；Omnigent 自身的侧边栏与织境二级侧边栏
  如何协调（`sidebarConfig` 不提供任意布局控制，见 2026-11-01 修订）；经 `bff` 转发时 Omnigent 如何识别用户；在织境主题下的显示效果。嵌入接口随上游变化的风险由锁定
  版本与升级时的回归测试控制。

## 修订（2026-10-31）：004 拆分交付与元数据采集提前

此前信息架构与统一 Web / BFF 边界保持；原 004 的交付清单由下表替代。旧章节中的功能编号应结合本修订阅读，
不再要求 004 一次交付搜索、审批、Agent 和终端。拆分的是 spec 与验收边界，不拆仓库、不新增微服务。

| 特性 | 交付 | 不作为本特性的完成条件 |
| --- | --- | --- |
| 004 Web 外壳与设计系统 | 四个一级入口、二级菜单、统一布局、亮色公共组件、账号 / 退出与公共状态；复用 001 会话 | 资产搜索、OM 待办、正式 Agent 嵌入、执行沙箱 |
| 006 资产搜索与摘要 | OM 风格浏览 / 搜索 / 组合筛选、排序分页、URL 恢复、资产摘要与统一实体选择 | Agent 对话、源库连接配置、业务行数据查询 |
| 007 Agent 工作台与页面助手 | OmnigentApp 与基础服务、BFF 代理与身份、会话级 MCP、页面上下文、侧栏与工作台同会话延续、四类结果组件 | 沙箱、终端、代码执行；完整运行持久化与恢复加固归 012 |

- **顺序**：004 → 005 → 006 → 007 → 008。005 由原数据接入阶段提前到 004 后，实现实际连接配置与元数据采集；
  资产搜索技术上不强制依赖 005，以便独立开发和测试。后续数据治理、上下文中心仍随业务特性加入导航。
- **搜索验收数据**：006 以 003 表定义生成测试元数据，通过开发工具幂等导入真实 OM，包含服务、表、字段及少量治理属性与术语。
  前端经 BFF 使用真实 OM 搜索 / 实体 API；该工具不作为用户连接入口，不包含连接凭证，不默认写入客户环境，
  不把元数据登记等同于数据源连通。005 的实际采集结果也经同一套搜索接口展示，无需另建搜索链路。
- **交互规则**：无关键词浏览目录、有关键词按资产类型组织结果；位置与筛选叠加、同维度 OR / 跨维度 AND；
  列表、摘要与 Agent 使用同一实体（类型、ID、FQN）。侧栏与工作台共享会话，切换资产不改写历史消息的上下文。
  Tier 不直接等同于数据安全级别；对象实例查询仍属 027，业务数据查询仍经 009。
- **嵌入 spike**：004 提前验证 Vite / React / 路由兼容、BFF 转发与用户识别方案，影响技术栈的选择在 plan 中明确；

  在嵌入对话中渲染的扩展可行性输出 spike 结论，不因视觉一致性要求直接扩大上游改动；确有功能缺口时按 2026-11-01 修订评估最小补丁。

## 修订（2026-11-01）：确认方案 B，明确嵌入与二次开发边界

负责人在两方案源码调研后确认：**采用方案 B，织境自建主应用，嵌入 Omnigent 完整工作台，并允许必要的受控二次开发。**
本修订取代此前“前端复用待决”“所有界面定制都由嵌入配置完成”“页面助手直接使用完整工作台”的表述；
004 → 005 → 006 → 007 → 008 的交付顺序与 012 的沙箱边界保持不变。

### 两方案取舍

| 方案 | 优点与代价 | 决定 |
| --- | --- | --- |
| A：以 Omnigent 为主应用，扩展织境业务页面 | 原生会话、文件与开发工作区可直接使用；官方浏览器扩展 V1 的网络与导航边界不足以直接承载织境业务页面，需新增受控通信 / 页面挂载接口或修改宿主。受控扩展不必然等于深度分叉，但业务信息架构更依赖上游 | 本期不采用；适用于以 Agent 开发工作区为产品中心的方向 |
| B：织境主应用 + OmnigentApp | 资产、治理、审批与上下文页面独立演进，延续 001 的 Web / BFF 基础；完整工作台复用上游，代价是构建、身份、状态与流式传输集成 | **采用**；契合当前产品规划 |

### 当前实现边界

- `apps/web/` 拥有主导航、路由、账号、设计系统和业务页面；整页 Agent 工作台通过 `OmnigentApp` 嵌入。
- 页面助手是织境的轻量交互组件，经 BFF 优先使用官方 `omnigent-client` / 已发布 API；与工作台使用同一个服务端会话 ID，
  消息和运行状态以 Omnigent 为准。BFF 负责上下文关联与适配，不另建 Agent 运行时或第二套会话正本。
- 发送消息时绑定当前资产的类型、ID、FQN 与上下文快照；切换资产不改写历史。历史恢复、流重连、消息去重、取消及
  侧栏 / 工作台切换需在 007 验证。业务结果组件先在织境助手与页面交付，嵌入对话的专用渲染只作扩展可行性验证。
- 工作台先保留上游默认样式，品牌使用服务端 `branding` 配置，明暗 / 路由 / 传输使用对应官方接口。
  `sidebarConfig` 只控制会话列表轮询、共享与分页等行为；它不提供任意导航替换、精简聊天布局或执行授权。
  嵌入接口没有现成的页面上下文或业务消息渲染参数，中文化与更深样式统一不作零改造承诺。
- 官方浏览器扩展 V1 运行于无网络访问的隔离 iframe，SDK 提供有限导航、会话摘要、项目与存储能力；
  不能直接请求 BFF、替换宿主 React 树或任意重组主导航，不能把该插件机制当作完整业务页面框架。
- 前后端定制都按“配置 → 官方扩展点 → 最小补丁”处理。扩展独立维护在 `extensions/`；补丁优先增加扩展接口，
  在 `third_party/omnigent/` 的发布分支登记并遵循上游优先规则。不复制上游 UI 到 `apps/web/` 长期维护。
- 所有浏览器业务流量经 BFF；签名身份桥接与下游委托身份分别校验。官方 OIDC 会话认证不等于原生接受任意
  Keycloak Bearer，静态 MCP header 不等于具备令牌续期 / 恢复能力。具体扩展与接线见 ADR-0002。
