# ADR-0009 仓库结构与代码架构

- 状态：已接受
- 日期：2026-10-07（2026-10-08 按单租户、组件统一管理、暂不做服务模板修订）
- 决策人：@stephenhuo-code
- 影响特性：全部
- 相关宪法条款：I（测试先行）、II（服务边界、契约先行）、III（许可）、VI（以服务方式集成、扩展与补丁目录）
- 相关 ADR：ADR-0007（Phase 1 单租户）、ADR-0012、ADR-0013

## 背景

Phase 1 自建的后端服务只有 `bff`（ADR-0012、0013），其余能力来自约 15 个开源组件。主要工作量因此在
“开源组件的集成、配置即代码与测试”，而不是“批量开发自建服务”。仓库结构按这一现实设计。

## 决策

### 1. 单仓（monorepo）目录

```text
apps/
  web/                         # 织境 Web（React，ADR-0003）；打包为 nginx 静态资源镜像，独立部署；含复制自 Omnigent 前端的
                               # 代码（来源与许可记录在 apps/web/THIRD_PARTY.md）
services/
  bff/                         # Phase 1 唯一自建后端服务，也是代码架构的参考实现
  metric/  explore/            # 二期
packages/
  py-core/                     # 公共库 contexture-core（第 4 节）
  ts-api/                      # 前端 API 客户端，由 contracts 生成
pipelines/                     # 平台自带的 Airflow 管线（ADR-0006），构建为一个任务镜像
  dags/                        # DAG 定义（OM 元数据采集、接入物化、飞书同步、文档、治理、本体表结构）
  tasks/<域>/                  # 任务代码
agents/<名称>/                 # 织境 Agent 与数字员工模板：omnigent.yaml（内部 Agent）、paperclip.yaml（下发到
                               # Paperclip 的数字员工）、registration.yaml（负责人、用途，生成 Keycloak 客户端）
skills/                        # 给客户侧使用的参考 Skill（agentskills.io 格式）
contracts/
  openapi/<服务>.yaml          # 自建服务的同步接口契约
  mcp/                         # 对外 MCP 工具的契约（工具名、参数、结果结构；由 Toolbox 工具定义导出并评审）
  schemas/                     # 审计、错误等 JSON Schema
  otel/                        # 可观测关联属性规范
ontology/                      # 产品发布的标准层与领域包（从 OM 导出，不手工编辑，ADR-0008）
deploy/
  components/<组件>/           # 每个开源组件一个标准目录（第 2 节）
  helm/                        # 伞形 Chart：汇总全部组件与自建服务，一条命令部署整个环境
  terraform/aliyun/            # 测试环境云资源
  offline/                     # 离线安装包构建（镜像清单由各组件的 component.yaml 汇总）
extensions/
  openmetadata-connectors/     # OM 自定义连接器（帆软血缘、国产库等）
  omnigent-plugins/            # rollout 存储、OTel 导出、令牌交换等
  paperclip-plugin/            # Paperclip 轨迹插件：运行事件回传 Langfuse（ADR-0010）
third_party/                   # 打了补丁的上游组件（宪法 VI）
  openmetadata/
    src/                       # 子仓库：github.com/stephenhuo-code/OpenMetadata，分支 ctx/2.0.3
    UPSTREAM.yaml  PATCHES.md  build/   # 织境自己的登记与构建文件（不放进子仓库）
  omnigent/                    # 同上结构：src/ 为织境维护的 Omnigent 仓库（子仓库：stephenhuo-code/contexture-omnigent，分支 ctx/v0.18.0）
tests/
  e2e/                         # 跨组件端到端测试（含端到端骨架）
testdata/                      # 模拟工厂数据与模拟源系统（003）
tools/                         # CLI：环境初始化、Agent 登记同步到 Keycloak、数字员工下发到 Paperclip、回放等
docs/                          # 产品规划、计划、架构文档、ADR、调研
specs/                         # Spec Kit 特性规格
.specify/  .claude/            # Spec Kit 与 Claude Code 配置
.github/workflows/             # CI 流水线
pyproject.toml  uv.lock        # uv workspace 根（py-core、bff、pipelines、tools）
pnpm-workspace.yaml            # pnpm workspace 根
Makefile                       # 常用命令（如 skeleton-up、skeleton-test）
.gitmodules                    # 子仓库登记
```

- 每个目录只放一类东西：自建服务在 `services/`，开源组件的部署与配置在 `deploy/components/`，打了补丁的上游
  仓库在 `third_party/`，扩展代码在 `extensions/`。
- 客户在 Airflow 中自定义的管线不进本仓库：放在客户自己的仓库，由 Airflow 的 git-sync 拉取。`pipelines/`
  只放平台自带的管线。
- Phase 1 为单租户（ADR-0007 修订），仓库中没有按租户生成的配置。

### 2. 开源组件统一管理：每个组件一个标准目录

```text
deploy/components/<组件>/      # 如 openmetadata、keycloak、ai-gateway、toolbox、doris、langfuse、airflow……
  component.yaml               # 清单：版本（锁定）、镜像来源（官方 / 自建）、许可、
                               # 定制级别（配置 / 扩展 / 补丁，宪法 VI）、上游地址、负责人
  chart/ 或 Chart 引用          # 上游 Chart 的锁定版本，或织境自己的 Chart
  values/base.yaml             # 与环境无关的参数
  values/<环境>.yaml           # local、test、release-verify、customer 示例
  config/                      # 该组件的配置即代码（如 Keycloak realm 与 Agent 客户端、网关路由与策略、
                               # Toolbox 数据源与工具定义、OM 初始化）
  tests/                       # 冒烟测试与配置测试
```

- **配置即代码同样测试先行**（宪法 I）：
  - Toolbox 工具：用 Testcontainers 启动 Doris，按工具定义执行并核对结果；
  - AI 网关策略：允许 / 拒绝矩阵测试；
  - Keycloak realm：导入后实际做一次令牌交换，核对 `sub`、`azp`、受众。
- **CI 统一检查**：每个组件 MUST 有 `component.yaml`；版本已锁定；许可在白名单内；镜像列入离线包清单；带冒烟
  测试。缺任一项则构建失败。
- 打了补丁的组件（OM、Omnigent）另在 `third_party/<组件>/` 维护镜像仓库与补丁登记；`component.yaml` 指向
  自建镜像。

### 3. 自建服务内部分层（按需）

```text
services/<服务>/
  src/contexture_<服务>/
    api/        # HTTP 路由与请求 / 响应模型，与 contracts 保持一致（必有）
    adapters/   # 外部访问：OM、AI 网关（MCP）、Keycloak、Langfuse、Omnigent 等（必有）
    app/        # 用例编排（有多步编排时才建）
    domain/     # 领域模型与规则（服务有自己的领域逻辑时才建）
    main.py     # 组装：配置、公共库中间件、路由
  migrations/   # 数据库迁移（服务有自己的数据库时才建）
  tests/unit/ tests/contract/ tests/integration/
  Dockerfile
```

- 依赖方向：`api → app → domain`，`adapters` 实现 `app` 定义的接口；没有 `app` 时 `api` 直接调用 `adapters`；
  `domain` 不得引用 `api` 与 `adapters`。`bff` 以转发和聚合为主，Phase 1 只需 `api` 与 `adapters`。
- 跨切面能力一律来自 `contexture-core`，服务内不得自行实现令牌验证、令牌交换与关联属性。
- 访问实例与分析数据只能经 AI 网关以 MCP 调用（`contexture-core.mcp`，ADR-0013）；数据管线写入 Doris 除外。

### 4. 公共库 `contexture-core`

| 模块 | 能力 |
| --- | --- |
| `auth` | JWKS 验签；构建请求上下文：人（`sub`）、Agent / 服务（`azp`）、角色、`tenant_id`（取自 `config` 的常量）；拒绝无效令牌。授权范围、数据级别上限为二期预留 |
| `mcp` | 经 AI 网关的 MCP 客户端；以服务的 Keycloak 客户端身份做标准令牌交换并缓存 |
| `telemetry` | OTel 初始化；按 `contracts/otel/` 注入关联属性（含 `tenant_id` 常量）；异步边界与 MCP `_meta` 的上下文传递 |
| `ontology` | 本体模型、URI 规则与基本校验；经 OM API 读取已审批的本体并缓存（ADR-0008） |
| `errors` | 统一错误格式（`contracts/schemas/error.json`） |
| `config` | 配置加载与校验（环境变量 + 挂载文件，密钥来自 Secret / KMS）；提供部署级常量（如 `tenant_id`） |

- 使用方：`bff`、`pipelines`、`tools`；Omnigent 的令牌交换在 `extensions/omnigent-plugins/` 中复用 `auth` 与 `mcp`。
- 公共库有语义化版本；升级须在端到端骨架上回归通过。
- Phase 1 单租户，不设 `tenancy` 模块。

### 5. 契约与版本

- 自建服务的同步接口：先在 `contracts/openapi/` 提交并评审，再实现；URL 带主版本 `/v1`；同一主版本内只允许新增。
  CI 检测破坏性变更（oasdiff），并对服务做契约测试（Schemathesis）。
- **对外 MCP 工具同样是契约**：客户侧 Agent 直接调用这些工具。工具定义变更须先更新 `contracts/mcp/` 并评审；CI
  比对工具名与参数结构，删除或不兼容修改视为破坏性变更。
- 事件、审计、错误格式以 JSON Schema 定义。

### 6. 服务模板：Phase 1 不做

- Phase 1 只有 `bff` 一个自建服务，`bff` 即代码架构的参考实现；公共能力由 `contexture-core` 提供。
- 二期出现第二个自建服务（`metric`、`explore`）时，再从 `bff` 提炼服务模板（Copier）。

## 理由

- 公共库、契约、本体、组件配置需要与服务同步演进，单仓便于一次 PR 完成跨组件变更与回归。
- 开源组件数量基本固定且彼此差异大，用“标准目录 + 清单 + CI 检查”统一管理，比代码生成器更合适，也让配置与
  测试放在一起。
- 分层按需，避免为以转发为主的 `bff` 搭建空的领域层。
- 只有一个自建服务时，服务模板的维护成本大于收益。

## 考虑过的其他方案

| 方案 | 结论 |
| --- | --- |
| 多仓（每服务一仓） | 不采用：公共库、契约与组件配置的版本协调成本高 |
| 代码先行、从代码导出 OpenAPI | 不采用：违反宪法 II“契约先行” |
| 顶层 `config/` 与 `deploy/values/` 分开存放 | 不采用：同一组件的配置、参数与测试分散在多处 |
| Phase 1 即做服务模板 | 不采用：只有一个自建服务 |
| 用模板生成开源组件的部署目录 | 不采用：组件差异大，清单 + CI 检查即可保证不缺项 |
