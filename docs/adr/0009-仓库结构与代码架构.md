# ADR-0009 仓库结构与代码架构

- 状态：提议（待架构评审）
- 日期：2026-10-07
- 决策人：@stephenhuo-code
- 影响特性：全部
- 相关宪法条款：I（测试先行）、II（服务边界、契约先行）、VI（扩展与补丁目录）

## 决策

### 1. 单仓（monorepo）目录

```text
apps/
  web/                         # 织境 Web（React，ADR-0003）
services/                      # Python 后端服务（与架构文档一一对应）
  bff/
  metric/  explore/            # 二期
pipelines/                     # Airflow 管线（ADR-0006），构建为一个任务镜像
  dags/                        # DAG 定义（按域分文件：OM 元数据采集、接入物化、飞书同步、文档、治理、本体表结构）
  tasks/<域>/                  # 任务代码
packages/
  py-core/                     # 公共库 contexture-core：auth、telemetry、ontology、mcp（经 AI 网关的 MCP 客户端与
                               # 令牌交换）、errors、tenancy、config
  ts-api/                      # 前端 API 客户端，由 contracts 生成
contracts/
  openapi/<服务>.yaml          # 同步接口契约
  schemas/                     # 审计、错误等 JSON Schema
  otel/                        # 可观测关联属性规范
config/                        # 配置即代码（ADR-0003）
  keycloak/                    # realm 导出（租户、客户端、角色；每个 Agent 一个客户端）
  gateway/                     # AI 网关的路由、令牌校验、授权与审计配置（ADR-0013）
  toolbox/                     # MCP Toolbox 数据源与工具定义（含追溯查询模板）
  agents/                      # Agent 登记文件（负责人、授权范围、数据级别上限）
  openmetadata/                # OM 初始化：共用字段、hasProperty 关系类型、“数据级别”分类、域、Bot、工作流设置
agents/                        # 织境内部 Agent 的 Omnigent 定义（YAML）
skills/                        # 参考 Skill（agentskills.io 格式）
ontology/                      # 产品发布的标准层与领域包导出文件（从 OM 导出，不手工编辑，ADR-0008）
extensions/
  openmetadata-connectors/     # 自定义连接器（帆软血缘、国产库等）
  omnigent-plugins/            # 沙箱提供者、rollout 存储、OTel 导出等
third_party/                   # 上游组件（宪法 VI）
  openmetadata/                # 织境维护的 OM 仓库（子仓库，含 OKF v0.2 补丁）+ UPSTREAM.yaml、PATCHES.md、build/（ADR-0011、0012）
  omnigent/                    # 织境维护的 Omnigent 仓库（子仓库）+ UPSTREAM.yaml、PATCHES.md、build/（ADR-0002）
templates/
  service/                     # 服务模板（Copier）
deploy/
  helm/                        # 伞形 Chart；织境服务、OM、Omnigent 的 Chart；第三方组件的 values
  values/<环境>/               # local、test（阿里云）、release-verify、customer 示例
  terraform/aliyun/            # 测试环境云资源
  offline/                     # 离线安装包构建
tests/
  e2e/                         # 跨服务端到端测试（含端到端骨架）
testdata/                      # 模拟工厂数据与模拟源系统（004）
tools/                         # CLI：租户开通、Agent 登记同步、回放等
docs/                          # 产品规划、计划、架构文档、ADR、调研
specs/                         # Spec Kit 特性规格（spec、plan、tasks 等）
.specify/  .claude/            # Spec Kit 与 Claude Code 配置
.github/workflows/             # CI 流水线
pyproject.toml  uv.lock        # uv workspace 根
pnpm-workspace.yaml            # pnpm workspace 根
Makefile                       # 常用命令（如 skeleton-up、skeleton-test）
.gitmodules                    # 子仓库登记
```

- Python 用 uv workspace 管理（`packages/py-core`、各服务、`pipelines`），前端用 pnpm workspace。
- 每个目录只放一类东西：服务代码在 `services/`，配置即代码在 `config/`，上游组件在 `third_party/`，
  扩展在 `extensions/`；服务目录与 `docs/architecture/platform-architecture.md` 的服务目录保持一致。

### 2. 服务内部分层

```text
services/<服务>/
  src/contexture_<服务>/
    api/        # HTTP 路由与请求 / 响应模型，与 contracts 保持一致
    app/        # 用例：编排领域逻辑、事务边界、调用适配器
    domain/     # 领域模型与规则，不依赖框架与外部系统
    adapters/   # 外部访问：数据库仓储、OM、AI 网关（MCP）、Keycloak、Langfuse 等
    main.py     # 组装：配置、公共库中间件、路由
  migrations/   # 数据库迁移（Alembic）
  tests/unit/ tests/contract/ tests/integration/
  Dockerfile
```

- 依赖方向：`api → app → domain`，`adapters` 实现 `app` 定义的接口；`domain` 不得引用 `api` 与 `adapters`。
- 跨切面能力一律来自 `contexture-core`，服务内不得自行实现令牌验证与关联属性。
- 访问实例与分析数据只能经 AI 网关以 MCP 调用（`contexture-core.mcp`，ADR-0013）；数据管线写入 Doris 除外。

### 3. 契约与版本

- 同步接口：先在 `contracts/openapi/` 提交并评审，再实现；URL 带主版本 `/v1`；同一主版本内只允许新增。
- CI 检测破坏性变更（oasdiff）并对服务做契约测试（Schemathesis）。
- 事件、审计、错误格式以 JSON Schema 定义。

### 4. 公共库 `contexture-core`

| 模块 | 能力 |
| --- | --- |
| `auth` | JWKS 验签；构建请求上下文（人、Agent、租户、角色、授权范围、数据级别上限）；拒绝无效令牌与租户不匹配 |
| `telemetry` | OTel 初始化；按 `contracts/otel/` 规范注入关联属性；异步边界的上下文传递 |
| `mcp` | 经 AI 网关的 MCP 客户端；以服务的 Keycloak 客户端身份做标准令牌交换（访问实例与分析数据的唯一途径） |
| `errors` | 统一错误格式（`contracts/schemas/error.json`） |
| `tenancy` | PostgreSQL 行级安全会话变量、OM Domain 过滤封装、跨租户测试夹具 |
| `ontology` | 本体模型、URI 规则与基本校验；经 OM API 读取已审批的本体，按租户过滤并缓存（ADR-0008） |
| `config` | 配置加载与校验（环境变量 + 挂载文件，密钥来自 Secret / KMS） |

- 公共库有语义化版本；升级须在端到端骨架上回归通过。

### 5. 服务模板

- `templates/service/` 用 Copier 生成服务骨架，默认接入 `contexture-core`、健康检查、OTel、契约测试
  样例、Dockerfile 与 Chart；生成后测试即可通过。

## 理由

- 公共库、契约、本体、部署描述需要与服务同步演进，单仓便于一次 PR 完成跨服务变更与回归。
- 分层与依赖方向保证领域逻辑可单元测试（宪法 I），外部依赖可替换。
- 跨切面能力集中在公共库，保证宪法 IV、V 在所有服务中一致落实。

## 考虑过的其他方案

| 方案 | 结论 |
| --- | --- |
| 多仓（每服务一仓） | 不采用：公共库与契约的版本协调成本高 |
| 代码先行、从代码导出 OpenAPI | 不采用：违反宪法 II“契约先行” |
