# ADR-0006 三域数据治理与管线编排

- 状态：已接受
- 日期：2026-10-04
- 决策人：@stephenhuo-code
- 影响特性：001、005、009、010、011、012、013、014、016、018
- 相关宪法条款：III（开源许可）、IV（分级、审计、只用已审批内容）、V（可观测性）、VI（以服务方式集成、配置 → 扩展 → 补丁）
- 相关 ADR：ADR-0001（轨迹）、ADR-0004（本体与实例的存储分层）、ADR-0005（统一取数网关）

## 背景

计划中的特性覆盖了三域数据的接入与使用，但没有覆盖接入之后的持续治理：数据质量、敏感数据识别、
新鲜度监控、映射漂移、本体一致性、三域对齐质量、保留与清理，以及驱动这些工作的调度与自动化。

需要回答两个问题：

1. 各域的治理能力依赖 OpenMetadata 原有能力，还是需要二次开发。
2. 三域的接入与治理都是定时或事件触发的管线，由什么统一编排。

关于编排的现状：

- OpenMetadata 的采集逻辑在独立的 Python 采集框架（`openmetadata-ingestion`）中，按 YAML 配置
  运行，结果经 OM API 写回；OM Server 通过 PipelineServiceClient 接口对接编排器，现有实现为
  Airflow（`AirflowRESTClient` + `openmetadata-managed-apis` 插件）与 K8s 原生编排
  （`K8sPipelineClient`，1.12 起），也可关闭内置编排、由外部编排器运行采集框架。
- 产品规划记录“OM 2.1 将移除内置 Airflow，调度提前解耦”：问题在于 Airflow 与 OM **捆绑部署**
  （抢资源、版本绑定、扩容不便），而不是 Airflow 本身。
- 需要编排的不只是 OM 采集，还有实例物化（012）、飞书同步（010）、文档解析（016）、数据质量
  检查、漂移检测、保留清理。

## 决策

### 1. 统一编排器：独立部署的 Apache Airflow

- 采用 Apache Airflow（Apache 2.0）作为三域管线的**唯一编排器**，**独立部署**（KubernetesExecutor，
  每个任务一个 Pod），版本独立于 OM 升级；MUST NOT 使用 OM 内置的 Airflow。
- OM 采集由该 Airflow 调度：
  - OM 若仍支持外部 Airflow 的编排接口，则使用该接口，OM 中保留采集状态与触发能力；
  - 否则关闭 OM 内置编排（`PIPELINE_SERVICE_CLIENT_ENABLED=false`），在 DAG 中运行采集框架的
    容器镜像，配置以代码维护（ADR-0003）。
- 织境自有管线（实例物化、飞书同步、文档解析、数据质量检查、漂移检测、保留清理）以 Python DAG
  实现，任务以容器镜像运行；DAG 与配置纳入本仓库并走 PR。
- 通过 OM 的 Airflow 连接器把织境管线作为资产与血缘采集进 OM 目录。
- 管线失败、超时、积压 MUST 告警；运行数据经 OTel 进入可观测体系（宪法 V）。
- 访问数据源的任务遵守 ADR-0005：查询实例与分析数据经统一取数网关；写入本体实例库只由物化管线
  使用其专用写账号完成。

### 2. 治理能力按“能力 × 域”划分复用与自建

判断原则：数据若是 OM 能采集的资产（系统域源表、数仓表、Doris 本体实例库的表），优先复用 OM 的
治理能力；OM 看不到的数据（工作域原始内容、Agent 域）与 OM 没有的概念（本体层、跨域对齐）自建。

| 治理能力 | 系统域（源表、数仓） | 本体实例库（Doris） | 工作域（飞书） | Agent 域（轨迹、知识片） |
| --- | --- | --- | --- | --- |
| 数据质量检查 | 复用 OM（DQ as Code、测试套件、剖析） | 复用 OM（Doris 连接器支持剖析与数据质量） | 落库后复用 OM；原始数据自建 | 自建（样本与标注完整性） |
| 敏感数据识别与分级 | 复用 OM 自动分类，补充中文与工业场景规则 | 复用 OM 自动分类 | 自建：抽取时识别消息正文中的个人信息与敏感内容 | 自建：轨迹中的个人信息脱敏 |
| 新鲜度与 SLA | 复用 OM 数据契约（SLA）与剖析 | 复用 OM + 物化管线监控 | 自建：同步延迟 | 自建：采集延迟、Collector 队列积压 |
| 映射漂移 | OM 发现源表结构变化（变更事件）；“哪些映射因此失效”自建 | — | 自建：飞书接口字段变化 | — |
| 本体一致性（必填属性、关系完整、引用存在） | — | 自建规则，以 OM 数据质量自定义测试运行 | — | — |
| 三域对齐质量（如飞书人员与 MES 工号匹配率、置信度） | — | 自建 | 自建 | — |
| 数据契约 | 复用 OM（ODCS 导入导出） | 复用 OM | — | — |
| 保留与清理 | 客户源系统负责 | 自建：按租户的保留策略 | 自建 | 自建（Langfuse 数据保留策略为企业版功能，不使用） |
| 治理工作流（审批、认领、整改） | 复用 OM 治理工作流 | 复用 OM 治理工作流 | 进入审批中心 | 进入审批中心 |
| 自动化规则（如新表自动打标签、指派负责人） | OM 相关应用中哪些属于开源版待核实；Collate 的 AI 自动化为收费功能，不使用 | 同左 | 自建（二期） | 自建（二期） |

- 无论由哪个编排器运行，数据质量、剖析与自动分类的结果都经 OM API 写回 OM。
- 自建的检查（本体一致性、对齐质量、漂移）优先以 OM 数据质量自定义测试的形式实现，使结果统一
  落在 OM 并可在织境 Web 中展示（宪法 VI：扩展优先）。
- 治理发现的问题生成待办，进入审批中心统一处理（ADR-0003）。

### 3. Phase 1 与二期范围

**Phase 1（POC 必需）**

- 独立部署的 Airflow 及 DAG 规范；OM 采集、实例物化、飞书同步、文档解析、数据质量检查统一编排；
  管线失败告警。
- 复用 OM：核心对象表（批次、工单、检验、NCR）的数据质量与新鲜度检查；自动分类覆盖源表与
  本体实例库。
- 自建：映射漂移告警；P1 追溯链路涉及关系的本体一致性检查；三域对齐质量指标；工作域与轨迹中的
  个人信息识别与脱敏。
- 界面：数据治理中的“数据质量”“工作流”页面展示治理结果，待处理事项进入审批中心。

**二期**

- 数据契约强制执行与自动整改、自动化规则引擎、根因分析、完整的保留策略、SLA 看板。

### 4. 需要在 plan 阶段核实

1. OM 2.1 之后是否保留对外部 Airflow 的编排接口（`AirflowRESTClient` 与 managed-apis 插件）。
2. OM 的 Airflow 连接器与采集框架对 Airflow 3 的兼容情况。
3. 外部运行采集时，运行状态能否写回 OM。
4. OM 自动化与治理相关应用中，哪些属于开源版、哪些属于 Collate 收费功能。
5. OM 自动分类对中文字段与工业数据的识别效果。

## 影响

正面：
- 只有一个调度系统，三域管线的依赖、重试、告警与可视化统一。
- 与 OM 集成最好：采集可由同一编排器调度，织境管线可作为资产与血缘进入 OM 目录。
- DAG 使用 Python，与自建服务技术栈一致。
- 数据质量、分类、契约、治理工作流大量复用 OM，自建集中在本体层与 OM 看不到的数据。

负面与代价：
- Airflow 组件较多（调度器、API 服务、元数据库），需要纳入 Helm 与离线安装包，并有高可用方案。
- Airflow 大版本升级与 OM 集成的兼容性需要持续验证。
- 本体一致性、对齐质量、漂移检测、脱敏等自建工作量计入新特性。

## 考虑过的其他方案

| 方案 | 结论 |
| --- | --- |
| Argo Workflows | 不采用：K8s 原生、组件轻，但 OM 无原生集成，织境管线无法进入 OM 血缘；以 YAML 编排，数据管线能力（补跑、传感器、SLA）需自补 |
| OM 用 K8s 原生编排，织境管线另用编排器 | 不采用：调度分在两处，监控与告警要做两套 |
| 继续使用 OM 内置 Airflow | 否决：与 OM 捆绑部署、版本绑定，OM 2.1 计划移除 |
| Dagster / Prefect | 不采用：以资产或流程为中心，与 OM 的目录和血缘职责重叠，OM 集成不如 Airflow |
| K8s CronJob | 不采用：缺少依赖编排、重试与可视化 |
