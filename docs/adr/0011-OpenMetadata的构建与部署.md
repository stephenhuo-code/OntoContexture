# ADR-0011 OpenMetadata 的构建与部署

- 状态：已接受
- 日期：2026-10-07
- 决策人：@stephenhuo-code
- 影响特性：001、014、006、018、016、009
- 相关宪法条款：III（开源许可）、VI（以服务方式集成、上游镜像仓库，宪法 v1.2.0）、部署约束（离线可部署）
- 相关 ADR：ADR-0003、ADR-0004、ADR-0006、ADR-0007、ADR-0008
- 依据：[OpenMetadata 能力调研](../research/OpenMetadata能力调研.md)

## 背景

OpenMetadata 是织境的必选底座（宪法 III），承载本体、元数据、治理、上下文中心等能力。官方提供镜像与
Helm Chart（含依赖组件的打包）。织境需要跟随 OM 最新版本，并满足供应链可控、离线交付、多环境部署的要求。

## 决策

### 1. 从织境维护的 OM 仓库构建镜像

- 织境克隆并维护一个 OM 仓库（上游镜像仓库，宪法 VI 第 2 种方式），以子仓库（git submodule）挂在本仓库
  `third_party/openmetadata/`，锁定到具体提交；镜像从该仓库构建。
- 分支规则：

  | 分支 | 内容 | 规则 |
  | --- | --- | --- |
  | 主分支 | 与上游 `open-metadata/OpenMetadata` 同步 | 只同步上游，不提交织境改动 |
  | 发布分支 `ctx/<上游版本>`，如 `ctx/2.0.3` | 上游版本标签（如 `2.0.3-release`）+ 织境提交 | 构建从此分支产出；Phase 1 的织境提交只有 OKF v0.2 改动（ADR-0012），本体部分不改 OM 核心（ADR-0008） |

- `third_party/openmetadata/` 中另有：`UPSTREAM.yaml`（上游地址、当前版本标签、镜像仓库地址、许可）、
  `PATCHES.md`（发布分支上每个织境提交的登记：目的、上游 issue / PR、状态、删除条件）、`build/`（构建脚本
  与 Dockerfile）。
- CI 核对：发布分支相对上游版本标签的差异必须与 `PATCHES.md` 一一对应，否则构建失败。
- 改动须先向上游提 PR（从织境的 OM 仓库直接发起）；改动数量或规模持续增长、或连续两次升级出现冲突时，
  重新评估（宪法 VI）。
- CI 克隆子仓库时使用浅克隆，控制构建耗时与体积。
- 构建产物：

  | 镜像 | 内容 | 用途 |
  | --- | --- | --- |
  | `openmetadata-server` | Java 服务端（含随包的界面静态资源与 MCP 模块） | 常驻服务；也用于数据库迁移任务 |
  | `openmetadata-ingestion` | Python 采集框架（连接器、剖析、数据质量、自动分类） | 由 Airflow 按需拉起运行（ADR-0006） |

- 构建流水线：检出锁定的发布分支提交 → 核对补丁登记 → 构建 → SBOM、许可与漏洞扫描 → 推送到测试环境镜像仓库，并纳入离线安装包。
  镜像版本号为 `<上游版本>-ctx.<修订号>`。

### 2. 独立部署

- 使用织境自己的 Helm Chart（`deploy/helm/`）部署 OM，不使用官方的依赖打包 Chart：

  | 组件 | 部署方式 |
  | --- | --- |
  | OM 服务端 | 独立部署（可多副本）；数据库迁移以一次性任务执行 |
  | 数据库 | 平台共享的 PostgreSQL 集群中的独立 database `openmetadata` |
  | 搜索 | 平台共享的 OpenSearch 集群 |
  | RDF | Fuseki 服务器，开启 OM 的 RDF 索引应用，由 OM 同步本体与元数据（ADR-0008） |
  | 对象存储 | 测试环境 OSS / 离线 SeaweedFS，供上下文中心文件上传 |
  | 身份 | Keycloak（OM 的自定义 OIDC），织境服务以 OM Bot 令牌访问 OM |
  | 采集编排 | 平台独立部署的 Airflow（ADR-0006）；OM 编排客户端使用 Airflow REST 客户端或关闭内置编排 |
  | LLM 与嵌入模型 | 按需配置（语义检索需要）；Phase 1 可关闭 |

- OM 界面只对内部开放（ADR-0003）；OM 内置 MCP 服务在私有化交付中供客户 Agent 使用（ADR-0012）。
- 跟随策略：上游发布新的补丁版本时，主分支同步上游，基于新版本标签建立新的发布分支（有织境提交时变基），
  更新子仓库锁定的提交；次版本升级走 PR，在端到端骨架与本体相关验证通过后合并。

### 3. 理由

- 供应链可控：基础镜像、依赖、扫描、签名由织境统一管理，满足宪法 III 的 SBOM 与扫描要求。
- 离线与多环境：镜像与 Chart 统一纳入离线安装包，部署参数按环境配置。
- 与宪法 VI 一致：OM 作为独立服务集成；以上游镜像仓库方式维护，便于按官方方式构建与调试、直接向上游提 PR，
  同时以分支规则、逐提交登记与 CI 核对约束其不演变为深度分叉。
- 能快速跟随 OM 最新版本，而不受官方打包节奏与依赖组件版本的限制。

### 4. 许可边界（宪法 III 例外，已批准）

| 模块 | 许可 | 织境的用法 |
| --- | --- | --- |
| Java 服务端（全部 REST API） | Apache 2.0 | 复用 |
| JSON Schema | Apache 2.0 | 复用 |
| 界面静态资源（openmetadata-ui） | CCL 1.0 | 随服务端镜像构建，仅内部使用，不交付给客户使用 |
| 内置 MCP 服务（openmetadata-mcp） | CCL 1.0 | 随服务端镜像构建，在私有化交付中供客户 Agent 使用（ADR-0012） |
| Python 采集框架（ingestion） | CCL 1.0 | **复用**：用于私有化交付与内部测试环境的元数据采集、数据质量、自动分类 |
| AI SDK | CCL 1.0 | 不使用 |

宪法 III 规定“源码可用”类许可的组件不得成为交付物的硬依赖，例外须经架构评审批准并记录。**经决策人批准，
Python 采集框架作为例外使用**，条件为：

- 只用于私有化交付与织境内部测试环境，不对外提供与 Collate 竞争的在线服务（SaaS / PaaS）；
- 交付时保留其许可声明与版权声明；
- 界面静态资源随服务端镜像构建，不交付给客户使用；内置 MCP 服务在私有化交付中供客户 Agent 使用；
- 若产品形态改为对外在线服务，须重新评审本例外。

## 考虑过的其他方案

| 方案 | 结论 |
| --- | --- |
| 直接使用官方镜像与 Helm Chart | 不采用：依赖组件打包在一起，版本与配置受官方节奏约束，供应链与离线打包不可控 |
| 修改 OM 源码后构建 | 不采用：ADR-0008 已确定不改 OM 核心 |
| 以补丁队列维护（不建镜像仓库） | 不采用：镜像仓库更便于按官方方式构建、调试与向上游提 PR |
