# ADR-0013 数据访问与 AI 网关：Agent 经 MCP 取数，令牌用 Keycloak 标准交换

- 状态：已接受
- 日期：2026-10-08
- 决策人：@stephenhuo-code
- 影响特性：001、002、005、012、019、009、020、007、023、011
- 相关宪法条款：IV（身份、审计、Phase 1 例外）、III（开源许可）、VI（以服务方式集成）
- 修订：ADR-0005（005 的实现方式）、ADR-0012（取消自建 `sql-gateway`）；ADR-0002 中“SQL 经统一取数网关”改为经本 ADR 的数据访问路径

## 背景

ADR-0012 把 Phase 1 自建服务精简为 `bff` 与 `sql-gateway`。评审 `sql-gateway` 时发现：

- 它在 Phase 1 只剩“验证令牌、按租户路由、只读、限流、审计”，本身很薄；
- 客户的大量数据库会以 MCP 服务的形式提供给 Agent，自建 REST 网关覆盖不了这一场景；
- 主流数据库与云厂商已普遍提供 MCP 服务（Snowflake、BigQuery、Databricks、ClickHouse、MongoDB 为托管版；
  Oracle、SQL Server、Doris、StarRocks、OceanBase、达梦、PolarDB 等有可自托管的官方实现），Google
  MCP Toolbox for Databases（Apache 2.0）一个服务覆盖约 40 种数据源；
- 但 MCP 规范只统一协议与授权方式（OAuth、受众绑定、禁止转手令牌），**身份、审计、租户路由没有统一**：
  调研的数据库 MCP 服务都不在审计中记录 Agent（`azp`），也不能按令牌声明选择数据库账号。

同时需要确定 Agent 代表人调用时的令牌形式。

## 决策

### 1. 令牌：Keycloak 标准令牌交换，每个 Agent 一个客户端

- Keycloak 中没有专门的 Agent 实体，Agent 以 OAuth **客户端**表示（Keycloak 官方做法）。每个 Agent 登记为
  一个客户端（由 `config/agents/` 的登记文件生成），密钥由 Agent 运行时（Omnigent 服务端）保管，不下发给 Agent 执行进程。
- 人使用 Agent 时，Agent 运行时用人的登录令牌做**标准令牌交换**（Keycloak 正式支持、默认开启），得到：
  `sub` = 人，`azp` = Agent（Keycloak 签名），`aud` 收窄到目标服务，有效期短。人的登录令牌需通过受众映射
  包含各 Agent 客户端。
- 无人值守的 Agent（定时任务等）以服务账号（客户端凭证）运行，`sub` 为该服务账号，登记负责人。
- 不使用预览状态的委托交换（`act` 声明，Keycloak 26.8）；二期写回时再评估。

### 2. Agent 取数的标准方案：经 MCP

```text
Agent / 客户侧 Agent（交换后的令牌：sub = 人，azp = Agent）
  │ MCP
  ▼
AI 网关（同时作 MCP 网关与模型网关）
  校验令牌、按工具授权、路由、记录 人 / Agent / 工具 / 查询 / trace
  ├─► MCP Toolbox（只读数据库账号）──► Doris 本体实例库、客户数据库
  ├─► OM 内置 MCP
  └─► 其他厂商的数据库 MCP 服务（按 POC 需要接入）
```

- **AI 网关**：在 agentgateway（Apache 2.0，Linux Foundation）与 Agent Router（原 Envoy AI Gateway，Apache 2.0，
  建在 Envoy Gateway 上）中由 spike 选定一个。它同时承担**模型网关**（Omnigent 访问模型的唯一出口）。
- **数据库后端统一用 MCP Toolbox**（Apache 2.0）：主流库用其数据源；Doris 优先用其 mysql 数据源（Doris 兼容
  MySQL 协议，待验证），不可行时用 Apache Doris MCP Server（Apache 2.0）。Toolbox 不支持的库（如部分国产库、
  Hive）用厂商或社区的 MCP 服务，许可须符合宪法 III。
- **追溯等固定查询**以 Toolbox 的参数化工具定义（SQL 模板 + 参数），任意 SQL 只给需要的 Agent。
- **只读靠数据库账号**：Toolbox 使用 Doris 只读账号，workload group 按负载类型划分（Phase 1 单租户，ADR-0007）；
  应用层的只读检查只作补充（已知可被绕过）。
- `bff` 的页面查询同样作为 MCP 客户端经 AI 网关访问，平台只有一条取数路径。
- **不自建 `sql-gateway`**。Phase 1 自建服务只剩 `bff`。
- **不使用 LiteLLM 作网关**：其开源版的 JWT / OAuth2 认证与审计日志需商业许可（已核对源码）。

### 2a. 外部 Agent 平台的接入（见 ADR-0010）

- AI 网关遵循 MCP 授权规范对外提供服务：Keycloak 作授权服务器，网关提供受保护资源元数据，令牌受众绑定网关；
  外部平台可预先登记客户端，也可动态登记（按需开启）。
- 身份分三档：A 档每个 Agent 一个客户端（织境自有 Agent 与参考客户端）；B 档外部平台作为一个客户端代表人访问，
  `azp` 为平台，平台声明的具体 Agent 记录为未验证属性；C 档服务账号。网关审计按实际档位记录。

### 3. 模型接入

- 模型服务（OpenAI、DeepSeek 等 OpenAI 兼容服务商，以及私有化部署的模型）**只在 AI 网关中配置**：服务商地址、
  模型名、key、路由（按 Agent 或用途选择模型）与配额。key 存于 K8s Secret（测试环境由 KMS 管理），由
  `deploy/components/ai-gateway/` 的配置引用，不进仓库。两个候选网关均支持 DeepSeek 与 OpenAI。
- Omnigent 使用其“Gateway”凭证方式（OpenAI / Anthropic 兼容的地址加 key）连接 AI 网关，以委托令牌认证；
  Omnigent 与 Agent 都不持有厂商 key。
- **与 LiteLLM 基本对齐，只用网关自带能力，不额外开发**：
  - 一个 OpenAI 兼容入口统一多家模型；厂商 key 集中在网关；多个 key 或厂商之间故障切换；
  - 按人（`sub`）与 Agent（`azp`）控制可用模型、设置 token 配额（以 Keycloak 身份代替 LiteLLM 的虚拟 key）；
  - 不支持 OAuth 的客户端，使用网关自带的虚拟 key（若所选网关支持）；
  - 用量与费用统计直接使用 Langfuse（轨迹带人、Agent 与 token 用量）和网关自带指标，不自建花费报表；
  - 按月重置的花费预算、团队花费报表、自助申请 key 的界面等网关不具备的功能，默认不做。
- Phase 1 不做管理界面：更换 key、模型或配额即更新 Secret 与网关配置，经流水线部署（ADR-0003）。
- 需验证（并入 spike 第 4 项）：Omnigent 的网关凭证能否使用短期委托令牌并自动续期。

### 4. 审计

- AI 网关对每次 MCP 调用记录：人（`sub`）、Agent（`azp`）、租户、工具、查询内容摘要、trace_id；返回行数由
  后端结果或数据库审计补齐。若网关无法记录完整字段，以 Toolbox / 数据库侧日志补齐，按 trace_id 关联。
- 宪法 IV Phase 1 例外中的审计条款相应改为“取数入口（AI 网关）MUST 记录每一次调用”。

### 5. 不在 Phase 1 的内容

- 数据层授权（列级、行级、按数据级别）：二期；方向待定（候选：OM 审批后下发到 Ranger 或 Doris 原生权限）。
- BI 工具与 Notebook 的原生 SQL 通道（JDBC / Arrow Flight）：P2 的 023、024 再定。
- 管线临时 schema：数据管线在 Airflow 中直连 Doris（写入），不经 AI 网关。

## 理由

- 只自建框架不具备的能力：取数入口的身份、审计、路由由现成网关配置完成，数据库连接由 Toolbox 完成。
- 一条取数路径覆盖 Doris 与客户的各种数据库，以后接新库只是加一个后端。
- 网关集中处理身份与审计，避免给 Toolbox、Doris MCP、OM MCP 分别打补丁。
- 令牌方案只用 Keycloak 正式支持的功能，得到有签名的 Agent 标识，满足宪法 IV，无需例外。

## 考虑过的其他方案

| 方案 | 结论 |
| --- | --- |
| 自建薄 `sql-gateway`（REST） | 作为 spike 不通过时的后备；覆盖不了客户数据库经 MCP 访问的场景 |
| Agent 直接携带人的登录令牌 | 不采用：分不出人与 Agent，Agent 拿到人的全部权限，也不符合 MCP 规范的受众要求 |
| Doris 直接认 Keycloak 令牌（OIDC 插件） | 不采用：版本与能力未核实，审计记不下 Agent，需暴露 MySQL 端口 |
| OM Query Runner | 不采用：开源版只有接口定义，执行部分为 Collate 商业功能 |
| Trino、Kyuubi、Spice | Phase 1 不采用：偏重或关键能力收费；P2 联邦查询时再评估 |
| LiteLLM 作网关 | 不采用：认证与审计在开源版不可用 |

## 修订（2026-10-08，Phase 1 单租户，见 ADR-0007 修订）

- Phase 1 只有一个租户：一个 MCP Toolbox 实例、一个 Doris 只读账号，AI 网关不做租户路由；spike 第 2 项
  （按租户路由）取消。网关仍负责令牌校验、记录人与 Agent、聚合 MCP 服务与模型网关。
