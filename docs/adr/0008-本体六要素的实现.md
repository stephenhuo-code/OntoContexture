# ADR-0008 本体六要素的定义与实现

- 状态：已接受
- 日期：2026-10-07
- 决策人：@stephenhuo-code
- 影响特性：001、004、014、006、017、015、019、016、009、021、007
- 相关宪法条款：II（服务边界）、IV（只用已审批内容、租户隔离）、VI（配置 → 扩展 → 补丁）
- 相关 ADR：ADR-0003（OM 界面不交付）、ADR-0004（本体定义在 OM、实例在 Doris）、ADR-0007（多租户）、
  ADR-0011（OpenMetadata 的构建与部署）
- 依据：[OpenMetadata 能力调研](../research/OpenMetadata能力调研.md)

## 背景

- 织境的本体采用六要素：**对象、关系、属性、逻辑、动作、接口**，与 Palantir Foundry Ontology 的六个核心
  概念一一对应。
- OpenMetadata 2.0.3 不能新增实体类型；术语库支持层级（单父树）、可自定义的类型化关系、审批与版本；
  自定义属性按实体类型全局定义；没有逻辑与动作的模型。OM 自身的本体以 OWL + SHACL 表达，经 JSON-LD
  映射写入 Jena Fuseki（RDF 知识图谱，Beta）。
- 架构原则：尽量简单，能复用的就复用已有框架；Phase 1（P1 / P2）只读。

## 本体六要素的定义

| 要素 | 定义 | 举例 | 对应 Palantir 概念 | 实例（具体数据）存放 |
| --- | --- | --- | --- | --- |
| **对象** | 现实世界中的实体或事件的类型定义 | 设备、批次、工单、NCR | Object Type | 对象实例存于本体实例库（Doris），如设备 CNC-07 |
| **关系** | 两个对象之间关系的类型定义，含方向与基数 | 批次属于工单（多对一）、工单使用设备 | Link Type | 关系实例存于本体实例库（Doris），如批次 B2409-17 属于工单 WO-5521 |
| **属性** | 对象某一特征的定义，含数据类型、单位、是否必填、数据级别；一个属性可被多个对象共用 | 设备编号、型号、检验结果、缺陷数量 | Property（含 Shared Property） | 属性值随对象实例存于 Doris |
| **逻辑** | 以对象、关系、属性为输入的计算与判断，包括派生计算与校验规则 | “NCR 必须关联批次”、按检验记录派生“批次是否合格” | Function | 运行结果不单独存放；校验结果进入数据治理（ADR-0006） |
| **动作** | 对对象、属性与关系的一组受控修改及其副作用，含参数、前置校验与执行权限 | 生成扣款建议、调整 PO、发起停线审批 | Action Type | 每次执行记入决策轨迹与审计 |
| **接口** | 描述对象具备的共同形状与能力，一个对象可实现多个接口 | “可变更项”“成本载体” | Interface | — |

补充约定：

- 属性与源系统字段的对应称为**映射**，是本体的一部分，不是单独的要素。
- **指标**沿用 OM 的指标（Metric）实体，可引用对象与属性；**数据级别**沿用 OM 的分类标签。
- 本体只描述类型；按本体存入的具体数据称为**本体实例**（ADR-0004）。

## 决策

### 1. 分期范围

| 阶段 | 要素 | 理由 |
| --- | --- | --- |
| **Phase 1** | **对象、关系、属性（含映射）** | P1 追溯与 P2 取数只需要这三者；Phase 1 全程只读 |
| 二期 | 接口、逻辑、动作 | 接口用于 P4 工程变更；动作用于 P3 写回；逻辑用于自演进与复杂派生。P1 需要的基本校验（如“NCR 必须关联批次”）由 018 数据治理以 OM 数据质量测试完成，不作为本体的逻辑 |

六要素的定义、共用字段的枚举值、URI 规则在 Phase 1 即完整预留，二期不改概念。

### 2. Phase 1：本体在 OM 中的承载

**2.1 对象、关系、属性都建为 OM 术语。** 关系需要方向、基数与两端对象，而 OM 术语关系本身不能带属性，
故关系也建为术语。对象之间的继承用术语的父子层级表达。

**2.2 共用字段（术语的全局自定义属性）**，初始化时定义一次，所有术语共用，不适用的留空：

| 字段 | 类型 | 适用要素 | 含义 |
| --- | --- | --- | --- |
| `ctx_kind` | 枚举 | 全部 | 对象 / 关系 / 属性；预留接口 / 逻辑 / 动作（二期） |
| `ctx_uri` | 字符串 | 全部 | 统一资源标识，见 2.6 |
| `ctx_data_type` | 枚举 | 属性 | 字符串、整数、小数、布尔、日期、时间、枚举、引用 |
| `ctx_required` | 枚举（是 / 否） | 属性 | 是否必填 |
| `ctx_unit` | 字符串 | 属性 | 工程或业务单位 |
| `ctx_key` | 枚举（主键 / 显示 / 无） | 属性 | 在对象中的作用 |
| `ctx_cardinality` | 枚举 | 关系 | 1:1、1:N、N:1、N:M |
| `ctx_link_source` / `ctx_link_target` | 实体引用（术语） | 关系 | 起点与终点对象 |

**2.3 术语关系**：Phase 1 只使用一种自定义关系类型 `hasProperty`（对象 → 属性）。
`implementsInterface`、`operatesOn` 留到二期。

**2.4 数据级别**：属性术语贴 OM 分类“数据级别”的标签（一级 / 二级 / 三级）。

**2.5 映射**：源表字段关联对应的属性术语；字段的全局自定义属性记录映射信息：

| 字段 | 含义 |
| --- | --- |
| `ctx_object` | 该字段为哪个对象提供值（属性可被多个对象共用，必须指明） |
| `ctx_transform` | 转换规则（SQL 表达式） |
| `ctx_link` | 若该字段是关联键，对应的关系 |

**2.6 URI**：本体要素 `urn:ctx:<要素>:<领域包或租户>:<名称>`，要素取 `object`、`link`、`property`
（预留 `interface`、`logic`、`action`）；本体实例 `urn:ctx:obj:<租户>:<对象名>:<业务主键>`。

**2.7 组织方式**：标准层与每个领域包各为一个平台共享的术语库；每个租户在其域下有一个租户术语库，用于
扩展（ADR-0007）。

### 3. Phase 1：直接使用 OM 的本体能力，不另建本体服务

**原则**：Phase 1 只使用 OM 已有的本体能力（术语库、术语关系、自定义属性、审批与版本、RDF 知识图谱），
不额外增加新的本体能力——不另建本体服务，不另建本体的存储与编译链路，不自建推理与校验，先把 OM 的能力用好。
运行时由用户按需创建的数据与数据集不受此限制。织境只做
必要的集成：界面读写、按审批状态与租户过滤读取、生成 Doris 表结构。

| 职责 | 承担者 |
| --- | --- |
| 本体的读写 | 织境 Web → `bff` → OM API，直接写 OM 术语；`bff` 按租户域过滤（ADR-0007） |
| 审批 | OM 术语审批工作流与任务；织境审批中心展示 |
| 读取本体 | 公共库 `contexture-core` 的 `ontology` 模块经 OM REST API 读取术语、关系与共用字段，只返回**已审批**内容（宪法 IV），并在本地缓存；追溯（019）、上下文包（009）、物化管线（017）都经此模块读取 |
| 基本校验 | 同一模块：关系两端须为对象、必填、基数、共用字段合法；`bff` 提交前调用 |
| 实例库结构 | 一个 Airflow 任务经同一模块读取已审批的本体，生成 Doris 表结构与迁移脚本，经评审后执行（ADR-0004） |
| RDF 与 SPARQL | **使用 OM 自带的 RDF 能力**：开启 OM 的 RDF 索引应用，由 OM 把术语库等数据同步到 Fuseki（OM 的数据集），用 OM 的 SPARQL 接口做本体的查询、推理与性能验证 |

### 4. 用 OM 的 RDF 能力验证本体

开启 OM 的 RDF 知识图谱（Fuseki），用 OM 的 SPARQL 接口（`/v1/rdf/sparql`）验证本体的基本功能与性能：

| 类别 | 验证项 | 通过标准 |
| --- | --- | --- |
| 功能 | 导入标准本体（OWL / SKOS）与质量领域包，在 OM 术语库中建立对象、关系、属性 | 导入后的术语与关系完整 |
| 功能 | OM 将术语库同步到 Fuseki；用 SPARQL 查询对象的属性与关系、继承链、字段映射 | 与 OM 术语库一致 |
| 功能 | 推理：继承、逆关系（OM 内置 Jena 推理引擎；普通 SPARQL 查询是否带推理取决于 `inferenceEnabled` 配置，**待验证**） | 记录实际行为；能用则验证结果正确 |
| 功能 | 导出 Turtle / JSON-LD | 可供上下文包参考使用 |
| 性能 | 本体规模（数百对象、数千属性）的常用查询 | P95 ≤ 50 毫秒 |
| 性能 | 同步：术语变更到 Fuseki 可查询的延迟；全量重建耗时 | 记录基线 |

注意（已核实源码，见调研文档第 5b 节）：OM 的 RDF 能力为 Beta；全部 RDF 接口只对管理员开放、不按域过滤；
RDF 同步不区分草稿与已审批；重建索引会清空整个数据集。因此 Phase 1 的 RDF 只用于内部验证与探索；产品功能
读取本体一律经 `contexture-core.ontology` 调用术语 REST 接口（支持按 `entityStatus` 只取已审批内容，并按租户
域过滤）。

### 5. 生成 OKF 上下文包时对本体的使用

上下文包（009）经 `contexture-core.ontology` 读取已审批的本体：

| OKF 内容 | 来自本体的什么 |
| --- | --- |
| `type` 词表 | 对象（名称与 URI） |
| `resource` | 本体实例 URI 与其对象 URI |
| `relations` 扩展 | 关系（名称、方向、基数） |
| 正文中的字段名称、单位、显示顺序 | 属性的显示名、单位、主键与显示字段 |
| 生成前的列级过滤 | 属性的数据级别标签（与“人 ∩ Agent ∩ 数据级别”求值结合） |
| `verified` | 只读取已审批内容 |
| 版本与溯源 | 包内记录所依据术语的版本 |

```text
context（生成上下文包）
  ├─► OM：已审批的本体（经 contexture-core.ontology）、数据资产与指标的 AI 上下文
  └─► graph → gateway → Doris：本体实例与关系实例
```

### 6. 二期方向（届时另立 ADR 定稿）

| 要素 | 方向 |
| --- | --- |
| 接口 | OM 术语 + `implementsInterface` 关系；Fuseki 中以 `owl:Class` 与 `rdfs:subClassOf` 表达，支持多实现 |
| 逻辑 | 统一以 SHACL 表达：校验用形状约束，派生用 SHACL 规则或 SPARQL CONSTRUCT；规格存于新建的 ontology 服务，并在 OM 登记以复用审批；届时评估是否需要织境自己的 RDF 数据集 |
| 动作 | 以织境词汇 `ctx:Action` 表达（参数、修改范围、前置条件、副作用），可导出为 MCP 工具描述；规格存于 ontology 服务，并在 OM 登记 |
| ontology 服务 | 二期引入逻辑与动作时建立，承担规格存储、校验执行与动作接口；Phase 1 的公共库模块迁入其中 |

## 理由

- Phase 1 只需对象、关系、属性，全部能以 OM 术语原生表达；审批、版本、目录、字段关联、血缘复用 OM。
- 直接使用 OM 的本体能力：读写走 OM API，RDF 与 SPARQL 用 OM 自带的 Fuseki 同步，不另建本体服务与编译链路。

## 考虑过的其他方案

| 方案 | 结论 |
| --- | --- |
| Phase 1 即实现六要素 | 不采用：逻辑、动作、接口在 P1 / P2 用不到，增加复杂度 |
| Phase 1 建立独立的 ontology 服务 | 不采用：剩余职责可由 OM 与公共库承担 |
| 织境另建 Fuseki 数据集并编译写入 OWL | 不采用：Phase 1 用 OM 自带的 RDF 能力即可验证，二期引入逻辑时再评估 |
| 逻辑与动作以 OM 原生实体承载（测试定义、指标、MCP 工具） | 不采用：逻辑需按类型拆到不同实体，本体不直观 |
| 六要素全部存于织境，OM 只保留副本 | 不采用：违背“与 OM 保持一致” |
| 新增 OM 实体类型（改核心） | 不采用：补丁大、跟随上游难 |
| 本体文件放在代码仓库维护再同步到 OM | 不采用：同一份本体存在两处；审核人是业务人员 |

## 影响与需要验证

- 014 的范围为：初始化共用字段与 `hasProperty` 关系类型、公共库 `ontology` 模块、Doris 表结构生成任务、
  织境 Web 本体页面（经 `bff` 读写 OM）、开启 OM 的 RDF 能力并完成第 4 节的验证。
- `bff` 承担本体写入与租户过滤；OM 术语结构的解析集中在公共库，OM 升级时须回归。
- **需在 014 的 plan 中验证**：
  1. 租户在自己的术语库中为平台共享的对象增加属性时（`hasProperty` 从共享术语指向租户术语），是否会修改
     共享术语、触发其重新评审、对其他租户可见；若是，改为在租户术语一侧建立反向关系。
  2. 术语的父子层级能否跨术语库（租户对象继承平台对象）。
  3. OM 的 RDF 同步对术语自定义属性与关系的覆盖，以及变更同步到 Fuseki 的延迟。

## 修订（2026-10-07，见 ADR-0012）

- 第 5 节“生成 OKF 上下文包”改为复用 OM 的资产 AI 上下文，OKF 升级到 v0.2 的改动在织境维护的 OM 仓库中实现（ADR-0012 第 2 节）；本体部分仍不改 OM 核心。
- 读取本体的消费方中，追溯查询以 MCP Toolbox 的参数化工具经 AI 网关执行（ADR-0013），不再有 `graph`、`context` 服务。
