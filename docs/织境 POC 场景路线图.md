# 织境 POC 场景路线图

Sep 30, 2026 · @coderyan

## 排序逻辑

五个场景按"只读 → 可信 → 写回 → 深本体 → 自演进"递进，每个场景验证织境一项新能力，并复用前一个场景已建的本体与数据。场景选自《制造业 AI 全景蓝图》质量域 12 个子场景与财务域 5 个子场景与 Palantir 八类工业场景的交集。

| 优先级 | 场景 | 验证的能力 | 为什么排在这里 |
| --- | --- | --- | --- |
| P1 | 质量问题追溯与 8D 协同 | 三域合一、决策轨迹 | 只读、痛点普遍、不碰写回风险，最快证明"三域在一张图上"的价值 |
| P2 | 探索式报表：ad hoc → 确认 → 上线 | 可信语义（指标审批、受治理取数） | 直接重构现有"spec → 数仓规划 → SQL → 帆软"链路，逐出"口径谁说了算"并落地指标审批 |
| P3 | 供应商来料质量 → 采购与应付联动 | 写回动作、Agent 级权限 | 第一次让 Agent 改系统，金额明确、审批链清晰，需要 P2 的口径与权限基础 |
| P4 | 工程变更的质量与成本影响评估 | 工业本体深化（BOM / 工艺 / 版本） | 依赖本体深度，对标 Palantir 最硬的数字（BOM 审批 200h → 15s） |
| P5 | 质量知识自演进 | 自演进回流、本体提案 / 合并 | 横向能力，需前四个场景积累的纠正数据才有素材 |

明确不做的：取代数仓（织境是数仓之上的语义与取数层）、取代帆软固定报表与看板（只接管它们的语义层和即席问数）。

## P1 质量问题追溯与 8D 协同：详细设计

P1 只读不写，目标是把一次质量问题涉及的系统记录、人和讨论放在一张图上，让数字员工一次拿到全部上下文。以下规模与人员为单工厂、单事业部 POC 的估算。

**触发与流程**

1. 触发：QMS 新建 NCR / 客诉单，或飞书客诉群里有人 @ 数字员工。
2. 数字员工调用 Context API，以 NCR 为入口取回 OKF 知识包：批次 → 工单 → 工序 → 设备 → 检验记录 → 同批次历史问题 → 责任班组与工艺工程师 → 相关飞书讨论与审批。
3. 数字员工草拟 8D 的 D1–D4（小组、问题描述、围堵、根因候选），推到飞书；质量工程师修改。
4. 修改前后版本、引用的上下文、采纳 / 驳回通过轨迹回传写入图谱。

**三域联动数据**

| 域 | 来源系统 | 对象 / 记录 | 字段粒度 | 新鲜度 |
| --- | --- | --- | --- | --- |
| 系统 | QMS | NCR / 客诉、缺陷类型、8D 历史 | 单号、批次号、缺陷码、数量、责任工序 | 小时级 |
| 系统 | MES | 工单、批次、工序报工、设备使用、操作工 | 工单号、工序码、设备码、开完工时间、工号 | 小时级 |
| 系统 | MES / LIMS | 检验记录、SPC 数据 | 检验项、实测值、判定 | 小时级 |
| 系统 | ERP | 物料、供应商批次、销售订单 | 物料码、供应商码、客户 | 日级 |
| 系统 | 时序库（可选） | 设备关键参数 | 点位、时间窗 | 分钟级 |
| 工作 | 飞书 | 客诉群消息、审批（让步 / 报废）、组织架构、班组名单 | 消息、发送人、时间、审批节点、岗位 | 分钟级 |
| 工作 | 文档库 | SOP、控制计划、历史 8D | 文档 →知识片 | 日级 |
| Agent | 数字员工平台 | 调用事件、草稿版本、人工修改 diff、采纳结果 | 事件级 | 实时 |

**本体规模（估算）**

| 项 | 数量 | 说明 |
| --- | --- | --- |
| 对象类型 | 约 14 | 工厂、产线、工位、设备、物料、批次、工单、工序、检验记录、缺陷、NCR、8D、人员、岗位 / 班组（含飞书消息与审批 2 类则 16） |
| 关系类型 | 约 20 | 批次-工单、工单-工序、工序-设备、设备-产线、批次-检验、NCR-批次、NCR-缺陷、缺陷-根因、人员-岗位、班组-工序、消息-NCR、审批-人员等 |

| 缺陷 / 根因术语 | 50–150 条 | 从 QMS 缺陷码表与历史 8D 导入，SKOS 层级 |
| 动作类型 | 0 | 只读；8D 草稿写在飞书，不写回 QMS |
| 实例规模 | 工单 10⁷ 级 / 年，检验记录 10⁸ 级 | POC 只加载近 6–12 个月 |

**人员投入（估算，8 周）**

| 角色 | 人数 | 投入 | 职责 |
| --- | --- | --- | --- |
| 产品 / 场景负责人 | 1 | 50% | 场景定义、验收、客户对接 |
| 本体 / 数据建模 | 1 | 100% | 对象与关系定义、字段映射、术语导入 |
| 集成工程师 | 2 | 100% | QMS / MES / ERP 连接器、飞书连接器、轨迹回传 |

## P2 探索式报表：ad hoc → 确认 → 上线

P2 把"先定义再验证"反过来变成"先探索再固化"：数据已在数仓，需求方不再凭想象写 spec，而是在数字员工里看着数据把问题问准，确认有用的那一版才进入帆软上线。返工从链路末端移到前端。

**链路前后对比**

| 环节 | 现在 | 语义层 + Agent | 谁做 |
| --- | --- | --- | --- |
| 需求定义 | 业务凭想象写需求 spec | 业务在数字员工里边问边看，几轮对话把问题问准 | 业务 + Agent |
| 数据探查 | 工程师人工查表、验证口径、出样例 | Agent 按已审批口径 + 血缘直接出 ad hoc 结果，附带用了哪些表和口径 | Agent |
| 数仓架构规划 | 工程师从头看表 | 仅"需新建指标"进入；Agent 基于血缘给出建模草案，工程师审核 | Agent 草拟 + 工程师审 |
| 写 SQL | 人工逐张报表写 | 指标定义（口径 + 维度 + 关联）进指标语义模型并审批，SQL 由模型生成、网关执行，工程师只审不写 | 语义模型 + 工程师审 |
| 验证 | 报表做完再验证 | 结果出来即验证，无用的问题在这里终止 | 业务 |
| 上线 | 每个需求都走开发、对接帆软 | 反复被问、确认有价值的 ad hoc 结果一键打包为帆软数据集，报表只做可视化 | BI 开发 |
| 返工位置 | 链路末端，成本最高 | 链路前端，成本最低 | — |

**三个前提（即验收条件）**

1. **Ad hoc 结果可信**：Agent 在探索阶段只能用已审批口径，未审批的标注为"探索口径"；每个结果附血缘与口径。验收：指标审批流上线，首批 ≥ 30 个核心指标完成审批，问数准确率经业务抽检 ≥ 90%。
2. **探索过程被记录**：哪些问题被反复问、哪个结果被谁确认，由"Agent 事件与轨迹回传"写入图谱；它同时决定什么该固化，并为自演进提供输入（被反复使用的临时口径 → 提案进指标库）。验收：探索漏斗可查询。
3. **从 ad hoc 到上线一键完成**：确认后的查询、口径、维度自动打包成帆软数据集，不重写。验收：一个真实需求从探索到帆软上线不经人工 SQL。

**人员分工变化**

- 业务：自己完成探索和验证，不再写 spec。
- 数据工程师：从"按需求做报表"变为"维护语义模型 + 审核固化请求"，同样人力可支撑 3–5 倍需求量。
- 新增角色指标 owner（通常是业务分析师）：审批探索中沉淀的新口径。

**一次性准备**：数仓元数据接入（表 / 字段 / 血缘，OpenMetadata 连接器直接做）；把现有帆软报表的 SQL 反向解析为第一版指标库，这是自演进"自动装配候选语义、人审生效"的第一个用例。

**本体规模与人员投入（估算，8 周）**

| 项 | 数量 / 人数 | 说明 |
| --- | --- | --- |
| 数仓元数据 | 200–500 张表 | DWD / DWS 层为主，连接器自动采集 |
| 审批指标 | 首批 30–50 | 从帆软现有报表 SQL 反推，覆盖质量与财务核心口径 |
| 新增对象类型 | 2 | 指标定义、探索会话 |
| 帆软数据集映射 | 5–10 个 | POC 期内固化的报表 |
| 产品 / 场景负责人 | 1 人、50% | 指标审批流设计、验收 |
| 语义建模 / 指标工程师 | 1 人、100% | SQL 反向解析、指标模型、口径审批配置 |
| 集成工程师 | 1 人、100% | 数仓连接器、受治理查询网关、帆软数据集对接 |
| Agent 工程师 | 1 人、100% | 探索对话、SQL 生成与验证、固化打包 |
| 客户数据工程师 | 1 人、40% | 口径确认、建模草案审核 |
| 客户指标 owner（业务分析师） | 1–2 人、20% | 口径审批 |

合计约 6 人月乙方 + 1.5 人月客户。

## P3 供应商来料质量 → 采购与应付联动：详细设计

P3 是第一个写回场景：Agent 的建议经人审批后改 ERP，所以重点是动作定义、权限求值和事务回滚，而不是新增很多对象。复用 P1 的物料 / 批次 / 缺陷对象和 P2 的指标口径（来料不良率、质量成本）。

**触发与流程**

1. 触发：月度或批次级来料不良率超过已审批阈值（指标库中的口径），或 IQC 开出供应商不良单。
2. Agent 取上下文：供应商档案、近 12 个月来料检验、开放 PO 与在途、合同质量条款、历史扣款、采购员与供应商的飞书沟通。
3. Agent 生成建议：评级调整、扣款金额（按合同条款和质量成本口径）、PO 数量 / 交期调整、是否触发 8D 要求。
4. 三个动作走飞书审批：更新供应商评级（质量经理）、创建扣款单 / 贷项通知（采购 + 财务双签）、调整 PO（采购）。
5. 审批通过后经写回 webhook 进 ERP，失败则整体回滚；发票三单匹配时自动带出扣项。
6. 建议、审批结果、实际扣款回传图谱。

**三域联动数据**

| 域 | 来源系统 | 对象 / 记录 | 字段粒度 |
| --- | --- | --- | --- |
| 系统 | QMS / IQC | 来料检验、供应商不良单、SCAR | 检验批、抽样数、不良数、缺陷码 |
| 系统 | ERP 采购 | 供应商主数据、PO、入库单、价格、交期 | 供应商码、PO 行、单价、数量 |
| 系统 | ERP 财务 | 发票、应付、扣款 / 贷项通知 | 发票号、金额、匹配状态 |
| 系统 | 合同库 | 质量协议、赔付条款 | 条款 → 知识片 |
| 工作 | 飞书 | 审批流（评级 / 扣款 / PO）、采购-供应商沟通群、SQE 分工 | 审批节点、签字人、消息 |
| Agent | 数字员工平台 | 建议内容、引用口径、审批结果、写回回执 | 事件级 |

**动作与权限**

| 动作 | 参数 | 提交条件 | 写回目标 | 权限（人 ∩ Agent ∩ 数据级别） |
| --- | --- | --- | --- | --- |
| 更新供应商评级 | 供应商、新等级、依据 | 质量经理审批 | ERP 供应商主数据 | 质量经理具有权限 ∧ Agent 被授权该动作 ∧ 供应商数据为二级 |
| 创建扣款 / 贷项通知 | 供应商、发票、金额、依据批次 | 采购 + 财务双签；金额 ≤ 合同上限 | ERP 应付 | 同上，金额超阈值升级到财务总监 |
| 调整 PO | PO 行、新数量 / 交期 | 采购审批 | ERP 采购 | 采购员对该供应商有权 |

**本体规模（估算，在 P1 / P2 基础上新增）**

| 项 | 数量 | 说明 |
| --- | --- | --- |
| 新增对象类型 | 约 8 | 供应商、来料检验、SCAR、PO、PO 行、发票、扣款单、合同条款 |
| 新增关系类型 | 约 12 | 供应商-物料、供应商-PO、PO-入库-批次、发票-PO、扣款-发票、扣款-不良单、审批-动作等 |
| 动作类型 | 3 | 如上 |
| 指标口径 | 约 10 | 来料不良率、批次合格率、质量成本、扣款率、供应商综合评分等，均需审批 |
| 策略 | 约 6–8 条 | 按角色 × 动作 × 金额阈值 |

**人员投入（估算，8–10 周）**

| 角色 | 人数 | 投入 | 职责 |
| --- | --- | --- | --- |
| 产品 / 场景负责人 | 1 | 50% | 动作与审批流设计、验收 |
| 本体 / 数据建模 | 1 | 60% | 新增对象、口径定义 |
| 集成工程师 | 2 | 100% | ERP 写回 webhook（含回滚）、飞书审批对接 |
| 权限 / 安全工程师 | 1 | 60% | Agent 身份、策略求值、审计 |
| Agent 工程师 | 1 | 100% | 建议生成、金额计算、审批交互 |
| 客户采购 / SQE / 财务 | 3 | 15% | 规则确认、试运行审批 |

## P4 工程变更的质量与成本影响评估：详细设计

P4 的难点在本体深度：BOM 是多层、带版本、跨 PLM 与 ERP 两套来源的结构，变更影响要沿 BOM 向上、沿工艺路线向下、沿库存与在制向前三个方向遍历。复用 P1 的物料 / 工序 / 设备、P3 的供应商 / PO。

**触发与流程**

1. 触发：PLM 提出 ECR / ECN（零件换料、尺寸变更、供应商变更、工艺参数变更）。
2. Agent 遍历：受影响的上层物料 / 成品（where-used）、开放工单与在制、库存与在途 PO、受影响工序与控制计划、需重做的 PPAP 要素（PFMEA、控制计划、MSA、初始 Cpk）、历史同类变更的质量问题。
3. Agent 计算：单位成本变化（BOM 成本 + 工时 + 良率假设）、库存报废 / 改制金额、切换时点建议（What-if：立即 / 用完库存 / 按订单）。
4. 生成变更评审包推到飞书评审会；工艺、质量、采购、财务在包上批注。
5. 评审结论（批准 / 驳回 / 有条件）作为动作写回 PLM 变更状态，并创建 PPAP 重做任务。

## P5 质量知识自演进：详细设计

P5 不新建业务场景，而是把 P1–P4 里人对 Agent 的每一次纠正变成本体和指标库的提案，经人审生效。它在 P2 上线后即可开始积累数据，并行推进。

**三条回流**

| 回流 | 输入 | 提案内容 | 审核人 | 生效位置 |
| --- | --- | --- | --- | --- |
| 纠正回流 | P1 8D 草稿修改、P3 建议驳回理由、P4 评审批注 | 新缺陷类型、根因-设备 / 工序映射、口径修正、字段→属性映射修正 | 质量工程师 / 指标 owner | 本体分支 → 合并 |
| 自动装配回流 | P2 探索轨迹（反复被问的临时口径）、帆软 SQL、查询日志 | 候选指标、候选同义术语、候选关联 | 指标 owner | 指标库 |
| 新缺陷回流 | AOI / Novel Issue 输出的未知缺陷聚类 | 新缺陷类型 + 建议上位类 + 关联工序 | 质量工程师 | 缺陷术语表，跨厂发布 |

**机制**

1. 每条回传事件带 diff（Agent 原输出 vs 人改后）；提案生成器把 diff 归因到本体元素（哪个对象 / 关系 / 口径导致了错误）。
2. 同类纠正 ≥ N 次（默认 3）才生成提案，避免噪声。
3. 提案进本体分支，带影响范围（哪些知识包 / Skills 会变），人审合并；被驳回的提案也记录，避免重复。
4. 本体映射小模型（8B–14B）在累积 5k–20k 条人审样本后训练，接管点位 / 字段归类与实体对齐的初筛；之前用大模型 + 人审。
5. 北极星：上下文命中率上升、人工纠正率下降。

**三域联动数据**

| 域 | 数据 |
| --- | --- |
| 系统 | AOI / 视觉检测结果与图像引用、QMS 缺陷码表、帆软 SQL、数仓查询日志 |
| 工作 | 提案审核（飞书审批）、质量工程师 / 指标 owner 的岗位与授权 |
| Agent | P1–P4 全部回传轨迹、提案与采纳 / 驳回记录 |

**本体规模（估算）**

| 项 | 数量 | 说明 |
| --- | --- | --- |
| 新增对象类型 | 4 | 提案、纠正事件、本体版本、评估结果 |
| 新增关系类型 | 6 | 提案-影响元素、提案-证据事件、版本前后等 |
| 预期演进量 | 首年新增缺陷 / 根因术语 100–300 条、指标 30–50 个、映射修正数百条 | 来自 P1–P4 运行 |
| 训练样本 | 5k–20k 条 | 人审通过 / 驳回均可用 |

**人员投入（估算，持续 3–6 个月，与 P3 / P4 并行）**

| 角色 | 人数 | 投入 | 职责 |
| --- | --- | --- | --- |
| 平台工程师 | 1 | 100% | 提案生成器、本体分支 / 合并、影响范围计算 |
| 算法 / 模型工程师 | 1 | 60% → 100% | 归因、聚类、小模型训练与评测（参考 Jellyfish / LLMs4OL 方法） |
| 本体工程师 | 1 | 30% | 提案规范、合并规则 |
| 客户质量工程师 / 指标 owner | 2 | 10% 持续 | 审核提案 |

合计约 6–8 人月乙方，客户侧为持续低强度投入。

**验收**：提案采纳率 ≥ 50%；人工纠正率环比下降（目标半年 -30%）；小模型在点位归类 / 实体对齐上达到大模型 90% 以上准确率且成本低一个量级；新缺陷类型至少在第二家工厂复用一次。

## 本体规模与人员投入汇总

五个场景累计约 50 个对象类型、约 70 个关系类型、约 100 个审批指标、6 个写回动作；乙方约 40 人月、客户约 7–8 人月，其中 P4 占三分之一。所有数字为单工厂 POC 估算，多工厂推广时本体基本不增、集成与实例映射按厂递增。
